## 1. Status

This is the first draft of MAK-0007. The number was reserved by topic
before sequential numbering ([GOVERNANCE](../GOVERNANCE.md#protocol-standards-mak-xxxx)), and the
registry is approved future protocol scope, F-3
([ROADMAP](../ROADMAP.md#approved-future-protocol-scope)).

This draft:
- fixes the registry's **place** in the protocol;
- records what other standards have already **settled** for it;
- lists the **open decisions**.

It defines no API, schema or conformance criteria yet.

## 2. Purpose and scope

### 2.1 Purpose

A registry lets **published** knowledge be discovered, versioned and
reused across organizations: the npm-like model described in
[ARCHITECTURE.md](../ARCHITECTURE.md#the-registry-model-planned). It is the distribution channel for
reusable procedures, knowledge packs and history templates, so that teams
can check for and reuse existing work instead of regenerating it.

### 2.2 In scope (for this standard, when complete)

- What a registry entry is, and how it is identified, named and versioned.
- Publishing, deprecating and withdrawing entries.
- Discovery (search and lookup) and retrieval of a specific version.
- Installing or consuming entries into an organization or project.
- Visibility and access to entries.
- Integrity and trust metadata (who published what; whether it was
  verified).
- The interface binding(s) through which clients use a registry.

### 2.3 Out of scope

- **Organization-internal sharing.** Distributable artifacts shared within
  one organization are defined by
  [MAK-0009 §2.2](MAK-0009.md#2-knowledge-profiles) and don't require a registry.
- **Project records.** These stay in their project
  ([MAK-0005 Part A](MAK-0005.md#part-a--governed-project-records-normative)) and are never published to a
  registry directly.
- **Context assembly and applicability**
  ([MAK-0002](MAK-0002.md), [MAK-0003](MAK-0003.md)).
- **Hosting, pricing and operation** of any particular registry service.
  The protocol defines the contract; who runs a registry is not a
  protocol concern (see
  [docs/background/BUSINESS_MODEL.md](../docs/background/BUSINESS_MODEL.md)).

### 2.4 Terminology

| Term | Meaning in this draft |
|---|---|
| **Registry** | A service that stores published entries and makes them discoverable to principals beyond the publishing organization. |
| **Entry** | One published Distributable Artifact with its package versions. |
| **Publisher** | The organization (and authenticated principal) that published an entry. |
| **Package version** | The immutable semantic version of an entry ([MAK-0009 §2.3](MAK-0009.md#2-knowledge-profiles)). Never a project-record revision. |
| **Install / consume** | Bringing a registry entry into an organization or project so that it is available there. Semantics open (§4). |

## 3. Settled design

These points are already decided by other standards or by owner
decisions. They are the only normative content of this draft.

1. **What is published.** A registry entry is a Distributable Artifact,
   described by [MAK-0001](MAK-0001.md) packaging metadata and validated by
   [`artifact.schema.json`](../schemas/artifact.schema.json) (owner decision O-1, O-10).
2. **Identifiers.** Entry ids follow MAK-0001: `name` or `org/name`, where
   each segment is lowercase letters and digits joined by single hyphens
   ([MAK-0001](MAK-0001.md#required-fields)).
3. **Versions.**
   - Every published `package_version` is an immutable semantic version
     ([MAK-0009 §2.3](MAK-0009.md#2-knowledge-profiles)).
   - A registry MUST NOT change the content of a published version.
   - A registry MUST NOT treat a project-record revision as a package
     version.
4. **Identity and authorization.** Principals, authentication and
   permissions come from [MAK-0006](MAK-0006.md); a registry MUST NOT define a
   parallel identity model. Visibility rules MUST be defined consistently
   with MAK-0006. MAK-0006 has no teams and no per-individual visibility,
   so the visibility levels illustrated in [SPEC](../SPEC.md#access-control) need
   MAK-0006 support or a defined mapping first (§4).
5. **Provenance.**
   - Every published version carries authenticated provenance of the
     publishing principal ([MAK-0006 §7](MAK-0006.md#7-provenance)).
   - Client-reported names are unverified metadata.
   - MAK-0001 `author` is descriptive only and is never authorship.
6. **Organization boundary.**
   - Publishing to a registry is the **only** route by which knowledge
     crosses organizations.
   - Organization-internal inheritance ([MAK-0009 §1.4](MAK-0009.md#1-scope-hierarchy)) never
     does.
   - Consuming a registry entry MUST retain its source identity, package
     version and provenance, as MAK-0009 §2.2 requires for organization
     artifacts.
7. **No compliance or reuse guarantee.**
   - Check-before-create is a supported discipline today
     ([MAK-0008 §13.9](MAK-0008.md#13-client-requirements)).
   - A normative check-before-create rule is approved future scope that
     belongs with the registry (F-13). It is not yet part of this
     standard.
8. **No conformance yet.**
   - The Registry profile is future scope
     ([CONFORMANCE](../CONFORMANCE.md#conformance-profiles)).
   - No implementation may claim conformance to MAK-0007.

## 5. Implementation status

Nothing in this standard is implemented:
- **Registry and CLI.** No registry service, registry API, `publish` /
  `install` / `sync` command or registry MCP server exists in the protocol
  repository or the Reference implementation.
- **Sample metadata.** This repository contains sample MAK-0001 artifacts
  ([ARTIFACT_INDEX.md](../ARTIFACT_INDEX.md)), validated against `artifact.schema.json` by
  `scripts/validate_protocol.py`. That is packaging metadata, not a
  registry.
- **Organization sharing.** Distributable artifacts within one
  organization (MAK-0009) are architecture-defined and not implemented
  either.

No implementation may claim conformance to this document.

## Appendix A — Design notes (non-normative)

*Non-normative. Describes working ideas; nothing here is a requirement.*

- **Illustrative CLI** (from SPEC and ARCHITECTURE): `mak4i publish`,
  `mak4i install org/name`, `mak4i list`, `mak4i sync`. These names are
  illustrative and may change with M7-O1 and M7-O8.
- **Intended categories** (ARCHITECTURE "community marketplace"):
  - procedure packs (frontend, backend, infrastructure, AI, API gateways);
  - knowledge packs (compliance checklists);
  - history templates.
- **Security motivation.** Research on AI assistants hallucinating
  resource names, and on malicious agent "skills", suggests that a
  registry needs:
  - exact-name resolution from a trusted source;
  - publisher verification and integrity checks before installing
    (M7-O10, M7-O11; see
    [docs/background/COMPETITIVE_LANDSCAPE.md](../docs/background/COMPETITIVE_LANDSCAPE.md#security-positioning)).
- **Relation to skills.** First-class skills (F-6) would likely be
  distributed through a registry, but their object model is not defined
  and is not assumed here.
