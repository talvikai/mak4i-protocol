## 1. Status

**What this revision is.** Version 0.2 reconciles the v0.1 working draft
(September 2026, never published) with protocol v0.2 — [MAK-0004 Part A](MAK-0004.md#part-a--subject-conflicts-normative),
[MAK-0005 Part A](MAK-0005.md#part-a--governed-project-records-normative),
[MAK-0006](MAK-0006.md), [MAK-0008](MAK-0008.md) — and with the
architecture standard [MAK-0009](MAK-0009.md). The specification owner
directed its publication as Draft (In Progress). MAK-0003 is approved
future protocol scope F-2, targeted at protocol v0.3 together with
MAK-0002 (F-1) ([ROADMAP](../ROADMAP.md#approved-future-protocol-scope)).

**What changed from v0.1.**
- The v0.1 pipeline placed conflict handling *after* applicability. That
  contradicted MAK-0004 Part A, where conflicts are detected over all
  current heads before any filter. This revision treats conflicts as an
  input that MAK-0003 carries whole, never as a later stage.
- The output is renamed from "Resolved Set" (with `resolution_id` and
  `resolution_state`) to the **applicability result** (with
  `applicability_id` and an applicability state), because "resolution"
  means conflict resolution in MAK-0004.
- "A future access-control standard" is now [MAK-0006](MAK-0006.md);
  "workspace" is replaced by the organization / project / resource terms
  of [MAK-0009 §1](MAK-0009.md#1-scope-hierarchy).
- Lifecycle handling now uses the record states of
  [MAK-0005 §A6](MAK-0005.md#a6-lifecycle-states), the distributable
  artifact states of [MAK-0009 §2.2](MAK-0009.md#2-knowledge-profiles), and
  the discovery defaults of [MAK-0008 §10](MAK-0008.md#10-tool-catalog) (§10.6).
- All v0.1 design decisions and open questions move to §4 Open items.
  The v0.1 design material is kept, rewritten, as non-normative notes in
  Appendix A. Appendix B lists every change.

**What it is not.** It is not an accepted standard, not complete, and not
implemented. No conformance criteria exist. No implementation may claim
conformance to this document.

## 2. Purpose and scope

### 2.1 Purpose

MAK-0003 answers one question:

> Given a request in one project, and the MAK4I knowledge the requester
> is authorized to read, which knowledge applies to this request, and why?

MAK-0003 decides **what applies**. [MAK-0002](MAK-0002.md) decides **how
it is packaged**. The interface between them is the **applicability
result** (§3.8).

The title "Memory Resolution Algorithm" is the reserved title of this
number in [STANDARDS.md](../STANDARDS.md) and is kept. Despite the title,
this standard defines required *behavior and outputs*, not a specific
algorithm (Appendix A.2).

### 2.2 In scope

- The inputs that applicability determination draws on: the current
  knowledge result, history when explicitly requested, and MAK-0009
  inherited knowledge.
- How authorization, lifecycle state, conflicts and integrity errors
  constrain applicability.
- Selection of applicable knowledge, with a recorded rationale.
- The applicability result handed to MAK-0002.
- Open design questions: relevance signals, necessity, uncertainty,
  relationship expansion, bounds, determinism (§4).

### 2.3 Out of scope (non-goals)

- Packaging, ordering, size limits and representation of context
  (MAK-0002).
- Delivering context into an AI session ("injection"). This is not a
  certifiable client flow (§3.10).
- Detecting or resolving conflicts (MAK-0004). MAK-0003 never selects a
  winner.
- Lifecycle, supersession and record identity (MAK-0005).
- Identity, grants and provenance (MAK-0006).
- Rule inheritance and effective-rule computation (MAK-0009 §4).
- Transports and tool bindings (MAK-0008).
- Storage, indexing, retrieval or ranking technology. Vector stores,
  embeddings, search engines and particular models are implementation
  choices, never requirements.
- Agent orchestration and agent-to-agent communication.
- Guaranteeing that an AI system follows the knowledge it receives
  ([MAK-0009 §4](MAK-0009.md#4-rules-enforcement-and-inheritance), §4.9).

### 2.4 Terminology

| Term | Definition |
|------|-----------|
| **Applicability result** | The output of MAK-0003: the knowledge selected as applicable to a request, with rationale, plus the conflicts, integrity errors and effective rules it must carry. Identified by `applicability_id`. Its exact fields are open (M3-O1). |
| **Applicability state** | The overall outcome of one applicability determination (for example "applicable knowledge found" or "incomplete"). Its values are open (M3-O12). |
| **Applicable** | Selected as bearing on the request, with a recorded reason. |
| **Applicability rationale** | The recorded reason an item was selected. Distinct from MAK-0002's inclusion rationale, which records why an item is represented in a context package. |
| **Current knowledge result** | The result of `mak4i_get_current`: current records, open and resolving conflicts with their readable candidates, integrity errors and a reader instruction ([`context-package.schema.json`](../schemas/context-package.schema.json), title "Current knowledge result"; [MAK-0004 §A6](MAK-0004.md#a6-retrieval-of-conflicted-subjects)). |
| **Context package** | The MAK-0002 output structure, and only that. |
| **Conflict**, **candidate**, **`hidden_candidate_count`** | As in [MAK-0004 Part A](MAK-0004.md#part-a--subject-conflicts-normative) (A3, A5, A6.4). |
| **Record**, **revision** | A governed project record and its `version` (`"<n>.0"`), [MAK-0005 §A2](MAK-0005.md#a2-record-fields). |
| **Distributable artifact**, **package version** | Organization knowledge shared with the organization's projects, and its SemVer `package_version` ([MAK-0009 §2](MAK-0009.md#2-knowledge-profiles)). Never compared with a revision. |
| **Effective rule** | The rule that applies at a scope after inheritance, overrides and enforcement, with its explanation ([MAK-0009 §4](MAK-0009.md#4-rules-enforcement-and-inheritance), §4.6). |
| **Request** | What applicability is determined for, within one project. How a request (a task description, explicit references, a history flag) is represented is open (M3-O2). |

**About the word "resolution".** In protocol v0.2, *resolution* means
conflict resolution ([MAK-0004 §A7](MAK-0004.md#a7-resolution)):
`resolution_id`, resolution records, `resolving` conflicts. The word in
this standard's title is historical. To avoid a collision, MAK-0003's
output is the *applicability result*, its identifier is
`applicability_id`, and this document never uses "resolution" for its own
output or process. The v0.1 terms "Resolved Set", `resolution_id` and
`resolution_state` are retired.

## 3. Settled design

These requirements are inherited from merged standards and from the
owner-approved ROADMAP criteria ([ROADMAP](../ROADMAP.md#criteria-for-mak-0002-mak-0003-and-mak-0007)).
They restate those sources for MAK-0003. They add no new obligations to
existing implementations and are not assessed by CONFORMANCE.md.

### 3.1 Authorization and scope

- **S1.** Applicability is determined for exactly one project per
  request, by an authenticated principal (human, service or agent)
  ([MAK-0006 §4](MAK-0006.md#4-authentication-abstract); every tool of
  [MAK-0008 §10](MAK-0008.md#10-tool-catalog) takes one `project`).
  Cross-project determination is open (M3-O8).
- **S2.** Determining applicability requires `read` on the project, as
  part of the effective permissions: the live grant intersected with the
  transport ceiling ([MAK-0006 §5](MAK-0006.md#5-permissions-and-grants),
  §5.1, §5.3).
- **S3.** A request without `read` MUST fail without effect, with
  `access_denied`. It MUST NOT reveal whether the project exists, and the
  requester learns nothing about its knowledge
  ([MAK-0006 §5](MAK-0006.md#5-permissions-and-grants), §5.5;
  [MAK-0008 §9](MAK-0008.md#9-error-model); MAK-0004 D-007).
- **S4.** Knowledge never crosses an organization boundary. Organization
  knowledge reaches a project only through MAK-0009 inheritance, and
  project `read` covers the applicable distributable artifacts of that
  project, and only those ([MAK-0009 §1](MAK-0009.md#1-scope-hierarchy),
  §1.4; [MAK-0009 §4](MAK-0009.md#4-rules-enforcement-and-inheritance),
  §4.8).
- **S5.** In this revision, project grants are the only authorization
  unit: every reader of a project can read all of its records
  ([MAK-0006 §5](MAK-0006.md#5-permissions-and-grants), §5.4). Per-record
  restrictions are reserved (F-10). Rules about records a reader cannot
  read (S11) are forward-looking and MUST stay correct when such
  restrictions are added.
- **S6.** Resource and resource-group metadata MUST NOT be treated or
  presented as an access restriction
  ([MAK-0009 §7](MAK-0009.md#7-authorization-current-and-future), §7.3).

### 3.2 Conflicts are carried, never resolved

- **S7.** Conflict detection belongs to MAK-0004. It runs over all current
  heads of the project, before any filter, and does not depend on the
  request, filters or the client ([MAK-0004 §A3](MAK-0004.md#a3-detection),
  A3.1–A3.2). MAK-0003 MUST use the conflicts that MAK-0004 detection
  reports. It MUST NOT re-run detection differently, and its selection
  MUST NOT create, dissolve or change a conflict.
- **S8.** MAK-0003 MUST NOT select, merge or drop a candidate, and MUST
  NOT pick a winner — not by recency, author, revision, relevance or
  model judgment ([MAK-0004 §A1](MAK-0004.md#a1-scope),
  [MAK-0004 §A6](MAK-0004.md#a6-retrieval-of-conflicted-subjects), A6.1).
- **S9.** A candidate of an `open` or `resolving` conflict MUST NOT be
  presented as applicable current knowledge (A6.1). While a conflict is
  `resolving`, the subject is conflicted even if only one head remains
  ([MAK-0004 §A4](MAK-0004.md#a4-conflict-identity-and-state), A4.2).
- **S10.** If MAK-0003 selects *any* candidate of a conflict, it MUST
  carry the **whole conflict**, as a conflict,
  with all its readable candidates. A candidate MUST NOT appear without
  its conflict, including in any uncertain or bypass path. Selection
  never hides one side (the MAK-0004 A6.2 filter rule, applied to
  selection). The applicability result MUST make the conflicted state
  explicit (A6.3).
- **S11.** Unreadable candidates are disclosed only as
  `hidden_candidate_count`: their existence and number are disclosed,
  their identifier, title and content are not ([MAK-0004 §A6](MAK-0004.md#a6-retrieval-of-conflicted-subjects),
  A6.4, D-007). In this revision the count is 0 (S5). This is the one
  permitted disclosure about unreadable knowledge.
- **S12.** Integrity errors ([MAK-0005 §A7](MAK-0005.md#a7-integrity)) are
  surfaced as integrity errors and never resolved by guessing. A lineage
  with an integrity error contributes no current record; MAK-0003 MUST NOT
  present any of its versions as current. Integrity errors present in the
  input MUST be carried in the applicability result (ROADMAP criterion 1);
  whether all of them or only related ones are carried is open (M3-O9).
- **S13.** Rule conflicts are carried the same way. A rule key that
  MAK-0009 reports as `conflicted` at a scope is carried as conflicted
  with no candidate chosen; candidates reported as `blocked_by_mandatory`
  stay inspectable as such ([MAK-0009 §4](MAK-0009.md#4-rules-enforcement-and-inheritance),
  §4.6–§4.7; [MAK-0004 §A10](MAK-0004.md#a10-rule-conflicts-at-other-scopes-architecture-note)).
  Not assessable until MAK-0009 is implemented (S21).

### 3.3 Lifecycle and history

- **S14.** Record states are `active`, `superseded` and `withdrawn`.
  Only an `active` head whose subject is not in conflict is current
  ([MAK-0005 §A6](MAK-0005.md#a6-lifecycle-states)).
- **S15.** Superseded and withdrawn versions are never current
  knowledge. Until MAK-0002 is complete, implementations MUST NOT inject
  them as current ([MAK-0008 §10](MAK-0008.md#10-tool-catalog), §10.6).
  MAK-0003 MUST NOT select them as applicable current knowledge.
- **S16.** History (superseded and withdrawn versions, resolved conflicts)
  appears only when explicitly requested, and each historical item MUST
  be labelled with its status and, where set, its `resolution_id`
  (MAK-0008 §10.6). What counts as an explicit request is open (M3-O10).
- **S17.** Distributable artifacts are `active` (applies), `deprecated`
  (still applies, and should name its replacement in `deprecated_by`) or
  `withdrawn` (applies to no project; history kept)
  ([MAK-0009 §2](MAK-0009.md#2-knowledge-profiles), §2.2). Not assessable
  until MAK-0009 is implemented (S21).
- **S18.** MAK-0003 MUST NOT compare, order or convert a record revision
  against a package version ([MAK-0009 §2](MAK-0009.md#2-knowledge-profiles), §2.3).

### 3.4 Provenance

- **S19.** Each selected item keeps its own authenticated provenance
  ([MAK-0006 §7](MAK-0006.md#7-provenance)): `principal_id`,
  `principal_type`, `agent_id`, `display_name` snapshot, `auth_method`,
  `credential_id` or `oauth_client_id`, optional `client {name, version,
  verified: false}`, `recorded_at`. Legacy versions without provenance
  stay without it; provenance MUST NOT be fabricated (§7.5).
- **S20.** Client metadata (`client`) is never authorship and MUST NOT be
  used to establish it (§7.3). MAK-0001 `author` is packaging metadata,
  not provenance (ROADMAP criterion 3).

### 3.5 MAK-0009 inherited knowledge (architecture-defined)

- **S21.** MAK-0009 is an architecture standard with no binding and no
  conformance criteria ([MAK-0009 §8](MAK-0009.md#8-conformance-status-at-this-revision)).
  Every requirement in this subsection, and every requirement elsewhere
  that depends on MAK-0009, is **not assessable** until MAK-0009 is bound
  and implemented.
- **S22.** The applicable distributable artifacts of the project are an
  input ([MAK-0009 §2](MAK-0009.md#2-knowledge-profiles), §2.2):
  - an artifact applies to every project of its organization, or only to
    the projects in its `targets`; a project cannot opt out;
  - a project consumes the latest published `package_version`, unless it
    pinned one; an artifact carrying a `mandatory` rule always applies at
    its latest version; a pin to a withdrawn artifact has no effect.
- **S23.** An inherited item MUST keep its source identity
  (`organization_id`, `artifact_id`), its `package_version` and its
  provenance. MAK-0003 MUST NOT re-attribute it, re-version it or present
  it as a project record (§2.2).
- **S24.** Effective rules are a **required context category**, carried
  with their explanation: originating scope, enforcement, and each rule's
  status (`effective`, `overridden`, `blocked_by_mandatory`,
  `override_not_declared`, `conflicted`) with its provenance (owner
  decision U-15; [MAK-0009 §4](MAK-0009.md#4-rules-enforcement-and-inheritance),
  §4.6; ROADMAP criterion 12). MAK-0003 MUST take them as computed by
  MAK-0009 §4.6 and MUST NOT recompute them differently, infer rule
  relationships from wording, titles or tags (§4.2), or disclose a rule
  the requester cannot read (§4.8). How effective rules interact with
  task-based selection is open (M3-O7).

### 3.6 Terminology

- **S25.** "Context package" names only the MAK-0002 output. The
  `mak4i_get_current` result is the "current knowledge result". MAK-0003's
  output is the "applicability result", identified by `applicability_id`.
  MAK-0003 MUST NOT use `resolution_id` or "resolution" for its own output
  (ROADMAP criteria 5 and 6).

### 3.7 Boundary with MAK-0002

- **S26.** MAK-0003 decides *what applies*: selection with rationale, from
  the current knowledge result, history when explicitly requested, and
  MAK-0009 inherited knowledge, within the requester's authorization.
- **S27.** MAK-0002 decides *how it is packaged*: ordering, size,
  representation, partiality and explanation. MAK-0002 MUST NOT re-run
  applicability or conflict detection.
- **S28.** Selecting an item as applicable does not decide that it is
  included in a context package; inclusion is MAK-0002's decision.

### 3.8 The applicability result

- **S29.** The interface between MAK-0003 and MAK-0002 is the
  applicability result. It is distinct from the current knowledge result
  and from a context package. Its exact fields are open and shared with
  MAK-0002 (M3-O1); Appendix A.6 gives an illustrative, non-normative
  shape.

### 3.9 Delivery and compliance

- **S30.** Delivering a package into an AI session is out of scope.
  "Injection" is not a certifiable client flow; CONFORMANCE.md has no
  client-injection level (ROADMAP criterion 11).
- **S31.** MAK4I governs the content and explanation of applicable
  knowledge. It cannot guarantee that an AI system follows it, and
  documentation MUST NOT claim otherwise
  ([MAK-0009 §4](MAK-0009.md#4-rules-enforcement-and-inheritance), §4.9).

### 3.10 Conformance

- **S32.** CONFORMANCE.md has no criteria for MAK-0003, and no profile
  depends on it. Acceptance criteria will be written when the open items
  that block them are settled (M3-O20).

**Dropped or reframed v0.1 items.**
- **v0.1 D-006 / Q10 (uncertain items routed to, or bypassing, MAK-0004)
  — dropped as framed.** It assumed MAK-0004 runs downstream over
  "applicable artifacts". In v0.2 MAK-0004 detection runs upstream over
  all heads (S7), so nothing is routed to it. The part that remains —
  how an uncertain item that is a conflict candidate is carried — is
  settled by S10 (always with its whole conflict). The rest is M3-O6.
- **v0.1 D-005 / Q9 (canonical serialization)** — merged into M3-O1:
  protocol standards ship JSON Schemas (ROADMAP criterion 10).
- **v0.1 conformance list (11 items)** — removed; no criteria exist
  (S32). Its intent is carried by S1–S31 and M3-O20.
- **v0.1 "MAK-0004 scope TBD pending this standard"** — dropped. MAK-0004
  does not say this; "applicable artifact" is a Part B, non-normative
  term there.

## 5. Implementation status

No implementation may claim conformance to this document.

The Reference implementation (talvikai/mak4i-reference, protocol pin
`62fca93`) provides:
- `mak4i_get_current`: the current knowledge result — current records,
  open and resolving conflicts with all readable candidates, integrity
  errors, an instruction not to choose a side, and an optional opaque
  `resolution_trace`;
- `mak4i_search`: deterministic filters by `artifact_type`, tags (all of)
  and status (default `active`);
- `mak4i_history`: all versions of a lineage.

It has **no** relevance or applicability ranking, **no** task-based
selection, **no** relationship expansion, **no** size budget, **no**
truncation, **no** inclusion rationale beyond the opaque trace, **no**
uncertain-item handling, **no** context package, **no** inject command,
and **no** MAK-0009 inheritance or effective rules.

## Appendix A — Design notes (non-normative)

*Non-normative. Describes alternatives and working ideas; nothing here is
a requirement.* Where a note touches a settled item, the settled item
wins. The notes keep v0.1 material, rewritten to fit protocol v0.2.

### A.1 Conceptual model

One way to picture the flow end to end. It is not a mandated processing
order.

```
Request (one project, authenticated principal with read)        S1–S3
      │
      ▼
Inputs
  ├─ Current knowledge result (MAK-0004 §A6, MAK-0008 §10)
  │     current records · conflicts (all readable candidates
  │     + hidden_candidate_count) · integrity errors
  ├─ History, only when explicitly requested (MAK-0008 §10.6)
  └─ MAK-0009 inherited knowledge (architecture-defined)
        applicable distributable artifacts · effective rules
      │
      ▼
Applicability determination (MAK-0003)
  select what bears on the request, record why;
  conflicts carried whole; nothing resolved
      │
      ▼
Applicability result  ───────────▶  MAK-0002 packaging ──▶ context package
                                                            │
                                         delivery to an AI session (out of scope)
```

Conflict detection happens before this flow, in the server, over all
heads (S7). It is not a stage after applicability, as v0.1 drew it.

### A.2 Candidate discovery

v0.1 treated discovery as a behavioral contract, not a mechanism. That
idea still fits:
- the "candidate set" is a model, not a required object; candidates may
  be streamed or evaluated lazily;
- any mechanism is valid: exact identifier lookup, metadata filters
  (`artifact_type`, tags, `subject_key`), lexical or semantic search,
  embeddings, rule evaluation, model-assisted judgment, or hybrids;
- the inputs today are bounded by what one project's `read` covers (S5),
  so "candidate before authorization" (v0.1 §2.3) only matters once
  per-record restrictions exist (M3-O15).

v0.1's states, restated for v0.2:

| State | v0.2 meaning |
|---|---|
| Candidate | Knowledge in the inputs (A.1) that discovery found possibly related. |
| Eligible | Readable, in the project or inherited into it, and current (or historical and explicitly requested). Conflict candidates are eligible only as part of their conflict. |
| Relevant | Has one or more relevance signals for the request. |
| Applicable | Selected, with a rationale. |
| Excluded | Not selected. Never presented as applicable. |
| Uncertain | Possibly a state of its own (M3-O6). |

### A.3 Relevance signals and necessity

Candidate relevance signals from v0.1 — illustrative, **not** adopted
(M3-O3): `explicit_reference`, `active_requirement`, `active_constraint`,
`governing_decision`, `dependency`, `relationship`, `project_scope`,
`task_semantic_match`, `historical_request`, `applicable_policy`,
`continuation_context`. In v0.2, `applicable_policy` overlaps with
effective rules (S24) and `relationship` / `dependency` depend on M3-O11.

Relevance ("does this bear on the request?") and necessity ("can the
task be done correctly or safely without it?") are different axes. A
highly relevant background note may matter less than a low-profile
`mandatory` rule. v0.1 proposed three options for MAK-0003's role
(M3-O4):
- **A.** a minimal `necessary` / `not_necessary` / `unknown` indicator,
  narrower than a priority scheme;
- **B.** a graded criticality signal that could later seed MAK-0002's
  priority tiers;
- **C.** nothing here; priority is MAK-0002's alone.

Trade-off: too coarse gives MAK-0002 nothing to compute task sufficiency
from; too fine pre-empts MAK-0002's priority design.

### A.4 Applicability determination

v0.1 ideas that remain compatible:
- applicable is not the same as included: MAK-0002 may drop or truncate
  an applicable item for size, without making it less applicable (S28);
- an item not selected for lack of relevance and an item the requester
  cannot read should not be distinguishable — except for
  `hidden_candidate_count` on a conflict (S11);
- an uncertain item, if that state exists, must never be presented as
  confidently applicable, and must keep that status through packaging.

What changed: v0.1 said applicable items "proceed to MAK-0004" and
uncertain items "bypass MAK-0004". In v0.2 there is no downstream
MAK-0004 stage. Conflicts arrive already detected and are carried whole
(S7–S10).

### A.5 Explainability

Ideas carried from v0.1 (M3-O5):
- every applicable item has a reason: explicitly referenced; an active
  requirement governing the requested component; a current decision
  affecting the requested architecture; an effective rule at the target
  scope; history explicitly requested;
- **non-fabrication:** a rationale reflects the signals that actually
  contributed, not an explanation written afterwards (parallel to the
  same rule for MAK-0002's inclusion rationale);
- a rationale must not reveal unreadable knowledge;
- conflicts need no relevance rationale for their unselected
  candidates: they are carried because the subject was selected (S10).

### A.6 Illustrative applicability result

An illustrative shape only (M3-O1). Field names are not settled; JSON is
used for readability.

  "applicability_model_version": "0.2-draft",
  "computed_at": "2026-10-12T18:04:00Z",

  "project": "prj_pay",
  "request": {"task": "Add rate limiting to checkout endpoints",
              "explicit_refs": [], "history_requested": false},

  "bounds": {"reached": false, "dimension": null},

     "artifact_id": "rl-constraint", "version": "2.0", "status": "active",

     "applicability_rationale": {"reason": "Constraint on public endpoints of checkout"},

- `conflicts` follows MAK-0004 A5/A6. No candidate also appears in

- `history` would hold superseded or withdrawn versions only when

- There is no list of excluded items, and no count of them; the only
  disclosure about unreadable knowledge is `hidden_candidate_count`.
- `version` (revision) and `package_version` are separate fields and
  never compared (S18).

### A.7 Ambiguity, uncertainty, zero results and incompleteness

From v0.1, as working ideas (M3-O6, M3-O12, M3-O13):
- relevance can be genuinely uncertain: an ambiguous request, several
  plausible readings, thin metadata, a model-based judgment; a result
  should be able to say so rather than guess either way;
- three outcomes should not collapse into one:
  1. nothing applicable — determination finished and found nothing;
  2. indeterminate — the request is too ambiguous to evaluate;
  3. incomplete — something may exist but was not reached (a source
     failed, a bound was hit);
- an incomplete result is still usable if it says it is incomplete;
- "incomplete" is a natural input to MAK-0002's partial-context
  handling, without MAK-0003 computing MAK-0002's values.

Note: a request whose only matches are conflicted subjects is not "nothing
applicable": the conflicts are carried (S10).

### A.8 Bounds and relationship expansion

v0.1 proposed: a required mechanism bounding discovery, traversal and
result size; numeric limits as configuration; a reached bound reported
(`bounds.reached`, `dimension`) and the state set to incomplete; cycle
detection; no expansion into unreadable or out-of-scope targets.

In v0.2 the only defined links are lineage links (`supersedes`,
`superseded_by`, `lineage_id`), resolution links (`merged_from`,
`resolution_id`), subject keys, and in MAK-0009 resource membership,
rule `overrides` and `deprecated_by`. Following a supersession link leads
to history, which needs an explicit request (S16). Following a subject
key leads to a conflict, which must be carried whole (S10). A general
relationship graph (depends-on, governed-by) does not exist (M3-O11).

### A.9 Determinism

Options (M3-O14): selection reproducible for the same request, project
state and permissions when mechanisms are deterministic; non-deterministic
steps (for example model-assisted judgment) disclosed as such and never
presented as deterministic. Whatever is chosen, the conflict and
integrity state carried is the deterministic MAK-0004/MAK-0005 output
(S7, S12).

### A.10 Examples

Illustrative, rewritten from v0.1.

- **A. Coding task.** "Add rate limiting to the checkout service's public
  endpoints." Semantic match selects a current constraint record; an
  organization API standard applies through inheritance (S22). The
  applicability result lists both with rationale.
- **B. Architecture question.** "Propose the auth model for a new
  multi-tenant service." An organization `mandatory` rule on tenant
  isolation is carried as an effective rule with its originating scope
  (S24); current project decisions are selected by relevance.
- **C. Explicit lookup.** "Use the `multitenant-slug-auth-pattern`
  artifact." The explicit reference is a strong signal (M3-O16). If that
  subject is in an open conflict, the conflict is carried whole and no
  candidate is presented as current (S9–S10).
- **D. Current decision.** "What is our current database standard?" The
  active head of that subject is selected; its superseded predecessor is
  not, because history was not requested (S15–S16).
- **E. Why a decision was made.** "Why did we choose Platform B?" If this
  counts as an explicit history request (M3-O10), the superseded
  Platform A version is carried as history, labelled `superseded`; a
  version withdrawn by a resolution is labelled `withdrawn` with its
  `resolution_id`.
- **F. Superseded decision in ordinary work.** An implementation task
  touching onboarding selects only the current Platform B record. The
  superseded version is not applicable (S15).
- **G. Another project.** The requester references a project they have no
  grant on: `access_denied`, nothing disclosed (S3). Referencing a second
  project they *can* read is outside one request today (M3-O8).
- **H. Ambiguous request.** "Fix the bug", with several plausible
  modules. Either an `uncertain` state (M3-O6 a/b) or a result marked
  indeterminate (M3-O12). If one plausible item is a conflict candidate,
  its whole conflict is carried (S10).
- **I. Zero result.** Nothing in the project or its inherited knowledge
  bears on the request, and there are no relevant conflicts: an empty
  `items`, state "none applicable".
- **J. Agent continuation.** Agent A records decisions; Agent B, given a
  task by some external mechanism, gets an applicability result over the
  same project. Both see the same conflicts and the same effective rules.
- **K. Relationship expansion.** Today only lineage, subject and (later)
  MAK-0009 links exist (A.8). A depends-on graph is M3-O11.
- **L. Bounded result.** If bounds exist (M3-O13), a reached bound marks
  the result incomplete; it never presents a truncated result as
  exhaustive.
- **M. Conflicted rule.** Two project-scope rule lineages share
  `rule_key` `logging.format` with no mandatory ancestor: the key is
  carried as `conflicted` with both candidates and no choice (S13).

### A.11 Agent handoff and A2A

MAK-0003 adds no handoff function. A continuation looks like this, with
any external trigger (A2A, MCP, a queue):

```
Agent A completes work → records stored in MAK4I (conflicts detected on write state)
   → Agent B receives a task (external mechanism)
   → MAK-0003: applicability result for one project
   → MAK-0002: context package
   → delivery to Agent B (out of scope)
```

Conflicts are not "resolved if necessary" between the steps: they stay
open until a principal with `resolve` resolves them
([MAK-0004 §A7](MAK-0004.md#a7-resolution)).

### A.12 Neutrality

MAK-0003 is model-, vendor-, cloud-, storage-, database-, transport-,
orchestration- and search-engine-neutral. It must not be read as
requiring a particular AI product, MCP, A2A, a vector database,
embeddings, a graph database or a cloud provider. Two implementations
with different discovery techniques should be able to produce equivalent
applicability results.
