---

## Abstract

This standard defines how a MAK4I artifact evolves over time —
identity versus version, canonical version representation, immutability,
lifecycle states, lineage, and compatibility — while preserving history
and allowing another MAK4I component to determine what is currently
applicable. It does not define conflict-resolution algorithms, context
injection, or registry/storage implementation.

---

## Motivation

Artifacts change. An organization's standards, decisions, and context
evolve, and MAK4I must represent that evolution without losing history
or creating ambiguity about what is currently authoritative. Without a
defined versioning and lifecycle model, [MAK-0004](MAK-0004-template.md) has no
reliable basis for determining supersession, staleness, or which of two
applicable artifacts should be treated as current — and MAK-0001's
existing `deprecated`/`deprecated_by` fields have no fuller lifecycle
model to sit within.

---

## Scope

This standard covers:
- The distinction between artifact identity and a specific version of
  that artifact
- Canonical version representation
- Immutability of published versions
- Lifecycle states and valid transitions between them
- Lineage metadata connecting versions to their history
- What constitutes a breaking vs. non-breaking change
- Supersession as distinct from mere recency
- Compatibility determination for consumers
- Rollback/reactivation behavior

---

## Non-Goals

MAK-0005 does NOT define:
- Artifact relevance ranking
- The conflict-resolution algorithm (see MAK-0004 — MAK-0004 consumes
  the outputs of this standard rather than this standard defining
  conflict behavior)
- Context injection (see MAK-0002)
- Registry implementation
- Storage backend
- SDK behavior
- MCP behavior
- Model-specific behavior

## Terminology

| Term | Definition |
|------|-----------|
| **Artifact identity** | The stable identifier for a conceptual artifact across all its versions — see §1 |
| **Version** | A specific, published revision of an artifact identity — see §1, §2 |
| **Lifecycle state** | The current status of a version (e.g., draft, active, deprecated, superseded) — see §4, still TBD in detail |
| **Supersession** | An explicit relationship where one version/artifact is declared to replace another, distinct from mere recency — see §8 |
| **Lineage** | The metadata connecting a version to its predecessor(s) and successor(s) — see §5 |

*Additional terms inherited from [MAK-0001](MAK-0001.md): `id`,
`version`, `type`, `deprecated`, `deprecated_by`.*

---

## Design Principles

- Artifact identity and version MUST be clearly distinguished — a
  version change does not create a new, unrelated artifact (§1).
- Once published/active, a version's content SHOULD be immutable;
  changes SHOULD create a new version rather than silently rewriting
  history (§3 — pending confirmation as a decision, not yet finalized).
- "Newer" MUST NOT be conflated with "superseding" — supersession MUST
  be explicit (§8).
- History MUST be preserved in a way that does not require loading all
  history into an AI session's context by default (§9).
- Compatibility determination MUST NOT be tied to a specific SDK or
  implementation (§12).

---

## Normative Requirements

### §1 Artifact Identity vs. Version

An artifact's identity (its `id`, per [MAK-0001](MAK-0001.md)) MUST
remain stable across versions. A version change MUST NOT be treated as
creating a new, unrelated artifact.

**Illustrative example (non-normative):**
```
company/api-gateway-policy

may have versions v1, v2, v3 — without becoming three unrelated
artifacts. All three versions share the identity
"company/api-gateway-policy."
```

This builds directly on `id` and `version` as already defined in
MAK-0001; this section does not redefine those fields, only clarifies
their relationship.

---

### §2 Version Representation

**DESIGN DECISION REQUIRED**

**Question:** Is Semantic Versioning (SemVer: MAJOR.MINOR.PATCH) the
canonical version representation for MAK4I artifacts, and if so, what
do MAJOR, MINOR, and PATCH actually mean for an AI artifact — as
opposed to a software package?

**Why it matters:** MAK-0001 already specifies `version` as a semver
string format, but format alone does not define semantics. Software
SemVer conventions (MAJOR = breaking API change) do not map cleanly
onto an artifact whose "breaking change" might mean a changed
organizational decision rather than a changed function signature.
Copying software SemVer semantics without adaptation risks specifying
something that doesn't actually help implementations or consumers
reason about compatibility (see §6, §7, §12).

**Possible approaches:**
- A: Adopt SemVer format (already implied by MAK-0001) and define MAK4I-
  specific semantics for each segment, tied to the breaking/non-breaking
  distinction in §6/§7.
- B: Adopt SemVer format but leave semantic meaning of each segment
  advisory/non-normative, since "breaking" is inherently more
  contextual for knowledge artifacts than for code.
- C: Define a MAK4I-specific versioning scheme that does not follow
  SemVer conventions at all.

**Trade-offs:** Option A gives the strongest interoperability guarantee
but requires §6/§7 to produce a precise, enforceable definition of
"breaking," which may be harder for knowledge/decision artifacts than
for software APIs. Option B is more honest about that difficulty but
weakens the guarantee consumers can rely on. Option C breaks
compatibility with MAK-0001's existing format assumption and would
require revising that standard.

**Rationale:** TBD

### §3 Immutability

**DESIGN DECISION REQUIRED**

**Question:** Once a version is published/active, must its content
remain immutable, with any change requiring a new version?

**Why it matters:** If published versions can be silently rewritten,
historical reconstruction (§9) becomes unreliable — a past AI session's
record of "what version did I read" would no longer correspond to
verifiable content. This is the recommended design principle under
evaluation, not yet a finalized decision.

**Possible approaches:**
- A: Strict immutability — any content change to a published version
  MUST create a new version; the old version's content is permanently
  fixed.
- B: Immutability with narrow, defined exceptions (e.g., metadata-only
  corrections such as fixing a typo in `description` do not require a
  new version, but `content` changes do).
- C: No immutability guarantee at the protocol level; left to registry
  implementations to decide.

**Trade-offs:** Option A gives the strongest historical-reconstruction
guarantee but may feel rigid for trivial corrections. Option B is more
practical but requires precisely defining what counts as "metadata-only"
versus a content change — which overlaps with §7 (non-breaking changes).
Option C is the most flexible but undermines the reliability goal in
§9 and weakens what "version" even guarantees across implementations.

**Decision:** TBD
**Rationale:** TBD

### §4 Lifecycle

**DESIGN DECISION REQUIRED**

**Question:** What is the complete set of lifecycle states MAK4I
recognizes, and what are the valid transitions between them?

**Why it matters:** [MAK-0001](MAK-0001.md) currently defines only a
boolean `deprecated` field and a `deprecated_by` reference — a
two-state model (not deprecated / deprecated). This standard's brief
calls for evaluating at minimum: draft, active, deprecated, superseded.
Whether MAK-0005 extends MAK-0001's existing fields, or introduces a
richer `status` field with more values, is unresolved and directly
affects MAK-0001 as well as MAK-0004 (which consumes this information).

**Possible approaches:**
- A: A minimal four-state model — draft → active → deprecated, with
  superseded as a special case of deprecated that also carries a
  `deprecated_by` reference (reusing MAK-0001's existing field).
- B: A richer state model with superseded as a fully distinct state
  from deprecated (a deprecated artifact may have no replacement; a
  superseded artifact always does), requiring a new field beyond what
  MAK-0001 defines today.
- C: States are advisory/non-exhaustive, and implementations MAY define
  additional states beyond a required minimum set.

**Trade-offs:** Option A is the smallest change to existing MAK-0001
schema but may not distinguish "deprecated with no clear replacement"
from "actively superseded," which §8/§9 depend on. Option B is more
precise but requires a MAK-0001 schema extension. Option C maximizes
flexibility but weakens cross-implementation guarantees MAK-0004 needs.

For each state (once decided), this standard must define:
- Meaning
- Whether it should normally be consumed by an AI session
- Allowed transitions (e.g., draft → active → deprecated, or
  active → superseded)
- Historical retention expectations

**Rationale:** TBD

### §5 Lineage

**DESIGN DECISION REQUIRED**

**Question:** What lineage metadata must a version carry to answer:
what existed before, what changed, what replaced it, and when did the
replacement become effective?

**Why it matters:** Without defined lineage fields, §9 (historical
retention) and §8 (supersession) cannot be mechanically verified —
lineage is the connective structure between versions.

**Possible approaches:**
- A: A minimal lineage set — `parent_version` and `supersedes` only.
- B: A fuller lineage set including `parent_version`, `supersedes`,
  `created_at`, `published_at`, and `effective_from`, distinguishing
  when something was authored from when it became authoritative (see
  §11).
- C: Lineage is derived implicitly from registry history rather than
  stored as artifact metadata fields.

**Trade-offs:** Option A is minimal but may not support the
created-vs-effective distinction §11 raises. Option B is the most
complete but adds several fields beyond MAK-0001's current schema.
Option C avoids schema growth but makes lineage dependent on registry
implementation, conflicting with the requirement that MAK4I remain
storage-independent.

**Decision:** TBD
**Rationale:** TBD

Candidate metadata under discussion (not finalized): `version`,
`parent_version`, `supersedes`, `created_at`, `published_at`,
`effective_from`.

### §6 Breaking Changes

**DESIGN DECISION REQUIRED**

**Question:** What constitutes an incompatible/breaking change for a
MAK4I artifact?

**Why it matters:** This directly determines correct use of the
version segment chosen in §2, and determines what a "compatible" or
"unsupported" version means for a consumer (§12).

**Possible approaches (categories to evaluate, not yet decided):**
- Removal of a required field
- Changed semantics of existing content, even if the schema is
  unchanged
- Changed behavioral requirement
- Incompatible schema change
- Change in the meaning of an existing field
- Changed scope or authority semantics (interacts with MAK-0004 §2,
  §3)

**Trade-offs:** Defining breaking changes narrowly (schema-level only)
is easier to check mechanically but misses semantic breaks that matter
more for knowledge artifacts than for code. Defining it broadly
(including semantic/meaning changes) is more accurate but much harder
to detect or enforce automatically, and may rely on human judgment at
publish time.

**Decision:** TBD
**Rationale:** TBD

### §8 Supersession

A newer version or artifact MUST NOT be treated as invalidating another
artifact merely because it has a newer timestamp or higher version
number. Supersession MUST be explicit.

**Illustrative example (non-normative):**
```
v1: "Platform A is the standard for new API onboarding."
v2: "Platform B is now the standard because Platform A is being
     retired." — v2 explicitly supersedes v1.

v1 remains part of history but no longer drives new onboarding
decisions once v2's supersession is recognized.
```

This section directly supports [MAK-0004 §7 and §9](MAK-0004-template.md),
which rely on explicit supersession (not recency) as a condition for
automatic resolution and decision continuity.

---

### §9 Historical Retention

MAK4I versioning MUST preserve enough history to allow another MAK4I
component to answer: what is true now, what was true previously, what
changed, when did it change, and what version did a previous AI/session
know — without requiring that full history be loaded into an AI
session's context by default.

Detailed context selection logic belongs to MAK-0002 (Context
Injection Specification — not yet drafted; see
[STANDARDS.md](../STANDARDS.md)),
not this standard. MAK-0005's responsibility ends at making the
necessary history *retrievable and structured*, not at deciding what
gets injected into a given session.

---

### §10 Deltas

**DESIGN DECISION REQUIRED**

**Question:** Should MAK-0005 normatively define how differences
between versions are represented, treat delta representation as
optional metadata, or defer it to another standard entirely?

**Why it matters:** A defined delta format could make version changes
easier for a consumer to reason about without diffing full content, but
adds specification surface that may not be necessary for MAK4I's core
goals.

**Possible approaches:**
- A: Delta representation is normative — every version MUST be
  accompanied by a machine-readable delta from its parent version.
- B: Delta representation is optional metadata — implementations MAY
  provide it, but MAK-0005 does not require it.
- C: Delta representation is out of scope for MAK-0005 and left to a
  future standard, if it's needed at all.

**Trade-offs:** Option A is the most useful for consumers but is a
significant new specification and implementation burden, and may not
generalize well across all artifact types (a delta on `content` for a
procedural artifact may look nothing like a delta for episodic
history). Option B is lower-cost but produces inconsistent support
across implementations. Option C avoids the problem but leaves a real
gap for consumers trying to understand "what changed" without external
tooling.

**Decision:** TBD
**Rationale:** TBD

**Illustrative example of what a delta *could* look like (non-normative,
not a proposal to adopt this exact format):**
```
Context v4: Database = MySQL
Context v5: Database = PostgreSQL

Delta:
  database:
    from: MySQL
    to: PostgreSQL
```

### §11 Time

This standard MUST clarify the distinction between when an artifact
version was *written* and when it became *authoritative/effective*.

Candidate temporal fields under discussion (not finalized, overlaps
with §5): `created_at`, `updated_at`, `published_at`, `effective_from`,
`deprecated_at`, `superseded_at`.

*Note: `created_at` and `updated_at` already exist as optional fields
in [MAK-0001](MAK-0001.md). Whether MAK-0005 reuses those directly or
introduces additional, more specific fields (`published_at`,
`effective_from`) is unresolved — see §5's Design Decision.*

### §12 Compatibility

**DESIGN DECISION REQUIRED**

**Question:** How does a consumer determine whether it understands and
can safely use a given artifact version?

**Why it matters:** Without a defined compatibility model, a consumer
encountering an unfamiliar or future version has no protocol-level way
to decide whether to proceed, warn, or refuse.

**Possible approaches:**
- A: Strict MAJOR-version compatibility — a consumer supporting MAJOR
  version N can safely consume any N.x.y, and MUST refuse or warn on
  any other MAJOR version.
- B: Explicit compatibility ranges declared per-artifact or
  per-consumer, similar to dependency-range syntax in software package
  managers, but without assuming a specific implementation.
- C: Compatibility is advisory only; MAK-0005 defines the *vocabulary*
  (supported, compatible, unknown, unsupported, future) but does not
  mandate consumer behavior for each case.

**Trade-offs:** Option A is simplest and directly leverages whatever
§2 decides for version semantics, but is only as good as §6/§7's
breaking-change definition. Option B is more flexible but adds real
specification complexity and risks becoming implementation-specific,
which conflicts with the requirement to remain SDK-independent. Option
C is the lowest commitment but provides the weakest interoperability
guarantee.

This standard MUST NOT tie compatibility determination to a specific
SDK or implementation, regardless of which option is chosen.

**Decision:** TBD
**Rationale:** TBD

### §13 Rollback / Reactivation

**DESIGN DECISION REQUIRED**

**Question:** When an organization decides to return to a previous
state, should the previous version become active again, or should a
new version be created that restores that previous state's content?

**Why it matters:** This directly affects the immutability principle
in §3 — if a past version can be "reactivated," does that mean its
lifecycle state (§4) changes retroactively, or does reactivation always
require a new version number, preserving the historical record
untouched?

**Possible approaches:**
- A: A prior version's lifecycle state MAY be changed back to active;
  version numbers themselves are never reused or rewritten, only their
  state changes.
- B: Rollback always creates a new version whose content restores the
  prior state; the prior version's own lifecycle state and history
  remain untouched.

**Trade-offs:** Option A is intuitive ("we went back to v1") but
means lifecycle state is not a strictly forward-moving property, which
complicates §4's transition model. Option B keeps history strictly
append-only and consistent with §3's immutability principle, but means
"v1" and "the currently active restoration of v1's content" are
formally different versions, which may be confusing without clear
documentation.

**Decision:** TBD
**Rationale:** TBD

**Illustrative example (non-normative):**
```
v1 → active
v2 → active, supersedes v1
v3 → restores the behavior described in v1

Does v1 become active again (Option A), or does v3 exist as a new
version containing the restored decision (Option B)? Not yet decided.
```

---

### §14 References / Dependencies

MAK-0005 MUST define enough compatibility behavior to support safe
references between artifacts — i.e., when Artifact A references a
specific version of Artifact B — without becoming a complete
dependency-resolution standard in its own right.

*This section is intentionally narrow in scope per the brief. Full
dependency-resolution behavior (version ranges across a dependency
graph, conflict resolution between transitive dependencies, etc.) is
explicitly out of scope for MAK-0005 and would require a future,
separate standard if needed.*

Note: [MAK-0001](MAK-0001.md) already defines an optional
`dependencies` field (an array of artifact IDs). Whether MAK-0005
extends this to reference specific *versions* (rather than just IDs)
is unresolved — see Open Questions.

## Interoperability Considerations

Because MAK4I is required to remain model-independent, tool-independent,
storage-independent, and provider-independent, this standard MUST
define versioning and compatibility *behavior* and *vocabulary* rather
than a specific database schema, registry implementation, or SDK
mechanism. Any decision made in §2, §4, §5, §10, or §12 MUST be
expressible without assuming a particular storage backend.

## Open Questions

1. Is SemVer the right representation, and what do MAJOR/MINOR/PATCH
   mean for a knowledge artifact rather than software (§2)?
2. Is immutability strict, exception-based, or left to implementations
   (§3)?
3. What is the full lifecycle state set, and does it require extending
   MAK-0001's existing `deprecated`/`deprecated_by` fields (§4)?
4. What is the minimal-vs-full lineage metadata set (§5)?
5. Is delta representation normative, optional, or out of scope (§10)?
6. What compatibility model does MAK-0005 adopt — strict major-version,
   explicit ranges, or advisory vocabulary only (§12)?
7. Does rollback reactivate a prior version's state, or always create a
   new version (§13)?
8. Should MAK-0001's `dependencies` field be extended to reference
   specific versions, not just artifact IDs (§14)?
