# MAK-0002 — Context Injection Specification

**Status:** Draft
**Version:** 0.1
**Created:** September 2026
**Author:** Aswin Kumar Balakrishnan, Talvik Inc.
**Type:** Core Standard

*This is a first working draft, circulated for review before it enters
the community comment period described in
[GOVERNANCE.md](../GOVERNANCE.md#how-changes-are-proposed). Sections
marked `DESIGN DECISION REQUIRED` are open questions, not settled
behavior. Everything else in this document is a proposed normative
requirement, not yet accepted.*

---

## Abstract

This standard defines how a **context package** — the assembled,
AI-consumable representation of MAK4I project information — is
constructed, ordered, sized, and annotated once the applicable
information for a task has already been identified. It governs the
*shape and construction rules* of usable context, not how that
information was found ([MAK-0003](MAK-0003.md)), how disagreements
between artifacts were resolved ([MAK-0004](MAK-0004.md)), or how an
artifact's lifecycle and version were determined
([MAK-0005](MAK-0005.md)).

MAK-0002 is AI-model neutral, vendor neutral, cloud neutral, transport
neutral, storage neutral, and orchestration neutral. It defines
*behavior*, not an SDK, a wire protocol, or a database schema.

**On the term "context injection":** within this standard, that term
refers to the *preparation and assembly* of AI-consumable context —
the process defined in this document. It does not refer to, and this
standard does not define, the physical transport or delivery of the
assembled package into an AI system (a system prompt, a tool result,
an MCP resource, a file, or any other mechanism). That remains
transport-specific and explicitly out of scope — see Non-Goals and
Processing Behavior.

---

## Motivation

MAK-0003 determines *what* information is relevant to a task. MAK-0004
determines *which version wins* when applicable information conflicts.
Neither defines what an AI system is actually handed once those
questions are answered. Without a defined answer:

- Every implementation invents its own context-assembly behavior,
  making MAK4I context non-portable between clients, registries, and
  models.
- There is no consistent way to tell current information from
  historical information, embedded content from a reference, or a
  complete package from a partial one.
- Truncation under a size limit becomes ad hoc, silently dropping
  whatever an implementation happens to drop first — including
  information that was authorization-restricted, safety-relevant, or
  load-bearing for the task.
- A future AI session has no reliable way to tell why a given piece of
  information appeared in its context, which undermines the decision
  continuity goal described in [MAK-0004 §9](MAK-0004.md#9-decision-continuity).

MAK-0002 exists to make context assembly predictable, auditable, and
consistent across implementations — not to make any particular AI
system's context window feel bigger.

---

## Scope

This standard covers:

- What categories of information a context package may contain
- How a context package is constructed from already-resolved,
  already-conflict-resolved information
- Ordering and prioritization within a package
- The distinction between current and historical information
- The distinction between embedded content and referenced content
- Size constraints and truncation/reduction behavior
- Provenance and authorization preservation through assembly
- Deterministic/reproducible assembly, where practical
- Handling of unavailable referenced content and partial context
- Declaring why information was included, and the package's own
  version

---

## Non-Goals

MAK-0002 does **NOT** define:

- Relevance or applicability determination (see
  [MAK-0003](MAK-0003.md) — MAK-0002 consumes its output)
- Conflict resolution between disagreeing artifacts (see
  [MAK-0004](MAK-0004.md) — MAK-0002 assumes conflicts are already
  resolved before assembly begins)
- Lifecycle, versioning, or supersession mechanics (see
  [MAK-0005](MAK-0005.md) — MAK-0002 consumes lifecycle state as an
  input)
- Access control policy or authorization decisions (a future access
  control standard — MAK-0002 preserves whatever authorization
  decision it is handed; it does not make one)
- Agent orchestration or multi-agent coordination
- Agent-to-agent transport (e.g., A2A) or any other transport
  mechanism
- Registry implementation, database implementation, or vector database
  implementation
- Any specific AI platform, model, or vendor (Claude, ChatGPT, Gemini,
  Grok, or any other)
- Any specific cloud provider
- How the assembled package physically reaches the AI system (system
  prompt, tool result, MCP resource, file, or any other transport —
  all are valid; none is assumed)

## Terminology

| Term | Definition |
|------|-----------|
| **Context package** | The complete, structured, AI-consumable assembly of context items produced by this standard for a given task and requesting identity — see §1 |
| **Context item** | One discrete unit of information inside a context package, belonging to one of the categories in §1 |
| **Resolved information** | The applicable, already conflict-resolved set of information handed to MAK-0002 as input, produced upstream by MAK-0003 and MAK-0004 |
| **Embedded content** | A context item whose full content is included directly in the package — see §5 |
| **Referenced content** | A context item that points to content by identifier/locator rather than including it — see §5 |
| **Inclusion rationale** | A recorded reason a context item is present in the package — see §13 |
| **Package version** | The semantic version of the MAK-0002 data model a given package conforms to — see §14, distinct from any artifact's own version |
| **Requesting identity** | The authenticated party (human or system) on whose behalf the package is assembled |
| **Partial package** | A context package that declares known, recorded incompleteness — see §12 |
| **Context insufficiency** | A declared condition, distinct from partiality, indicating that information necessary for correct or safe execution of the task is unavailable, unresolved, or excluded — see §12.4 |

*Additional terms inherited from [MAK-0001](MAK-0001.md): artifact,
`id`, `version`, `type`, `author`, `created_at`, `updated_at`,
`deprecated`, `deprecated_by`. Additional terms inherited from
[MAK-0004](MAK-0004.md): applicable artifact, authority, escalation.*

## Design Principles

- MAK-0002 assembles; it does not decide. Relevance (MAK-0003),
  conflict outcome (MAK-0004), and authorization are inputs, never
  computed here.
- A context package MUST be honest about its own limits. Silent
  truncation, silent omission, and silently stale historical
  information presented as current are all treated as defects, not
  acceptable implementation shortcuts — except where withholding a
  specific disclosure is itself required for authorization/security
  reasons (see §9.4), which is a deliberate carve-out, not a silent
  shortcut.
- Reference-only inclusion is a first-class outcome, not a degraded
  fallback — a package that points at content instead of embedding it
  is not automatically "worse," and this standard MUST NOT be written
  as though embedding is the default and referencing is the exception.
- The standard defines the *contract* a context package must satisfy,
  not the algorithm that satisfies it — two conformant implementations
  MAY assemble different but equally valid packages from the same
  inputs, as long as both satisfy the same guarantees (provenance,
  authorization, honesty about omissions).

## Normative Requirements

### §1 Context Package Contents

A context package MAY draw on any of the following categories. No
category is individually required to be non-empty — the presence and
volume of each is determined by what MAK-0003 resolved as applicable
for the task, not by this standard. A conformant context package
structure MUST be capable of representing every category below, even
when a given package uses only a few of them.

| Category | Description |
|----------|-------------|
| Project identity | What project/organization/workspace this context belongs to |
| Current project state | The current, active facts about the project (semantic-type information, per [SPEC.md](../SPEC.md#artifact-types)) |
| Active decisions | Decisions currently in force |
| Decision rationale | Why an active decision was made, where available |
| Active requirements | Requirements currently in force for the task or project |
| Active constraints | Constraints currently in force (technical, organizational, or policy) |
| Relevant artifacts | MAK-0001 artifacts determined applicable to the task |
| Artifact relationships | Dependency or relationship links between included artifacts |
| Relevant history | Episodic-type information (per SPEC.md) providing background |
| Supersession information | What has been superseded, and by what, without necessarily embedding the superseded content itself |
| Provenance | Source, authorship, and origin information for included items — see §8 |
| Applicable standards/policies | Organizational or protocol-level standards in force |
| Task-specific context | Information scoped to the specific task/session rather than the project generally |
| Context references/identifiers | Pointers to further content not embedded in the package — see §5 |

A context package MUST NOT introduce a category of information outside
this taxonomy without extending it via the process in
[GOVERNANCE.md](../GOVERNANCE.md); implementations needing additional
categories today MAY carry them as extension fields (see §15, Context
Package Data Model) pending standardization.

---

### §2 Context Package Construction

1. Construction MUST begin from resolved information already
   determined applicable by an upstream process (MAK-0003) and already
   conflict-resolved (MAK-0004). MAK-0002 MUST NOT re-run relevance
   determination or conflict resolution during assembly.
2. Construction is a transformation: resolved information in, a
   context package out. Given the same resolved input, the same size
   budget (§6), and the same ordering rules (§3), construction SHOULD
   be reproducible (§10).
3. A context package MUST declare a package version (§14).
4. A context package MUST NOT silently drop an entire category of
   resolved information available to it. If a category is empty, that
   MUST be distinguishable from a category that was resolved but
   excluded during assembly (e.g., by truncation, §7, or
   unavailability, §11).

---

### §3 Ordering and Prioritization

1. A context package MUST make the relative priority of its items
   determinable by a consuming system, rather than requiring that
   system to infer priority purely from structural position (which
   does not survive reformatting or reordering by the consumer).
2. Priority SHOULD be expressed as an explicit field on each context
   item, not only through document order.
3. Higher-priority items MUST NOT be truncated or reduced before
   lower-priority items are truncated or reduced first (see §7).
4. This standard does not mandate a fixed priority vocabulary (see
   Open Questions, §3 below); implementations MUST express priority in
   a way that at minimum distinguishes "required for the task to be
   attempted correctly" from "supporting/background."

**DESIGN DECISION REQUIRED**

**Question:** What is the canonical priority-tier vocabulary (e.g., a
fixed ordered set like `critical` / `active` / `supporting` /
`historical`, versus a numeric rank, versus something else)?

**Why it matters:** Without a shared vocabulary, two conformant
packages can express "this is essential" incompatibly, weakening
portability — the same problem MAK-0004 §3 identifies for scope
taxonomy.

**Possible approaches:**
- A: A small fixed set of named tiers defined by this standard.
- B: An open numeric rank, with only relative ordering meaningful.
- C: A hybrid — a small set of named tiers, each optionally refined by
  a numeric rank within the tier.

**Dependency:** Priority-tier vocabulary SHOULD be coordinated with
[MAK-0003](MAK-0003.md) once that standard is drafted — the relevance
signals MAK-0003 produces are a natural input to priority assignment,
and deciding a vocabulary before MAK-0003 exists risks a mismatch this
standard would then have to unwind. This decision (D-001) is
intentionally left unresolved until then.

### §4 Current vs. Historical Information

1. Every context item MUST carry a status distinguishing current/
   active information from historical information.
2. A historical item included in a package MUST be clearly marked as
   historical and MUST NOT be presented in a form indistinguishable
   from current, active information.
3. By default, a context package SHOULD include only current/active
   items. Historical items SHOULD be included only when the task
   explicitly calls for history (e.g., "why did we choose this"), or
   when a current item's meaning depends on referencing what it
   superseded.
4. When a decision has been superseded, the package MUST be able to
   represent that supersession occurred (§1, Supersession
   information) without being required to embed the full content of
   the superseded decision (see Example F).
5. This section records the *presentation* rule; the underlying
   lifecycle/supersession mechanics are defined by
   [MAK-0005](MAK-0005.md), and staleness/re-litigation avoidance is
   governed by [MAK-0004 §9](MAK-0004.md#9-decision-continuity).
   MAK-0002 does not redefine either.

---

### §5 References vs. Embedded Content

1. Every context item MUST declare whether its content is embedded
   inline (`embedded`) or provided as a reference/identifier to be
   resolved separately (`reference`).
2. Reference-only inclusion MUST be treated as a fully valid, ordinary
   outcome — not an error state or a degraded fallback (see Design
   Principles).
3. When content is embedded, the package SHOULD retain enough
   metadata (at minimum: source id, and version where applicable) to
   trace the embedded copy back to its authoritative source (see §8).
4. The decision of whether a given item is embedded or referenced is
   influenced by, but not identical to, the size constraints in §6 —
   an implementation MAY choose to reference something that would fit,
   for reasons outside this standard's scope (e.g., the source is
   expected to change frequently).

---

### §6 Context Size Constraints

1. A context package MUST be constructable against an explicit size
   budget supplied as an input to assembly. MAK-0002 MUST NOT assume
   or hard-code a specific consuming model's context window size.
2. The unit in which the budget is expressed is an assembly-time
   input, not a constant defined by this standard, because "tokens"
   are tokenizer- and model-specific and MAK-0002 MUST remain model
   neutral (see Open Questions).
3. Each context item SHOULD declare, or allow the assembler to
   compute, its own size cost in whatever unit the budget uses.
   [MAK-0001](MAK-0001.md)'s optional `token_estimate` field is one
   example signal an implementation MAY reuse; MAK-0002 does not
   require it.

**DESIGN DECISION REQUIRED**

**Question:** Should MAK-0002 define a canonical, model-neutral unit
of size cost (an abstract "cost unit"), or leave the unit entirely to
the assembling implementation?

**Why it matters:** Without a shared unit, "the same" resolved
information can produce packages that behave completely differently
across implementations under the same nominal budget, which weakens
comparability and testability.

**Possible approaches:**
- A: Leave the unit fully implementation-defined; the package records
  whatever unit was used.
- B: Define an abstract, tokenizer-independent cost unit that
  implementations map their own tokenizer/byte-count onto.
- C: Recommend (SHOULD, not MUST) a default unit (e.g., UTF-8 bytes)
  for interoperability while allowing override.

### §7 Truncation and Reduction Behavior

1. When resolved information exceeds the size budget (§6), the
   assembler MUST apply a defined, non-arbitrary reduction strategy
   rather than an undocumented or implicit cutoff.
2. Reduction MUST respect declared priority (§3): items MUST NOT be
   reduced or dropped ahead of a lower-priority item still present in
   full.
3. Reduction MAY convert an embedded item into a reference-only item
   (§5) as an intermediate step, before excluding it outright, when
   the referenced content remains resolvable.
4. Any item that is reduced or excluded during truncation MUST be
   recorded in the package (at minimum: item id and reason) so the
   omission is visible to a consuming system rather than silent (see
   §12, §13).
5. The specific algorithm used to select what reduces first *within* a
   priority tier (e.g., oldest first, largest first, lowest declared
   relevance first) is implementation-defined. MAK-0002 defines the
   constraints reduction must satisfy, not the algorithm that performs
   it — consistent with this standard's implementation-neutral scope.

---

### §8 Provenance Preservation

1. Every context item MUST retain provenance sufficient to trace it
   back to its source, at minimum: a source identifier, and — where
   available — a source version, author, and origin system.
2. Provenance MUST survive reduction (§7) and reference-only inclusion
   (§5). When an item is dropped entirely, a record of *that omission*
   (not the content) MUST still carry enough provenance to identify
   what was omitted (see §7.4, §12).
3. MAK-0002 uses [MAK-0001](MAK-0001.md)'s existing fields (`id`,
   `version`, `author`, `created_at`, `updated_at`) as its base
   provenance vocabulary and MUST NOT define a conflicting or
   duplicate provenance model.
4. Content presented in a package MUST NOT be attributed to a source
   that did not produce it. If content is summarized or compressed
   during assembly, the summary MUST be distinguishable from the
   original source content (see Security Considerations).

---

### §9 Authorization Preservation

1. Context assembly MUST NOT include content the requesting identity
   is not authorized to access.
2. Authorization is an upstream input to MAK-0002, not a decision it
   makes. MAK-0002 MUST preserve an authorization decision made
   elsewhere (a future access-control standard) rather than
   re-evaluating or second-guessing it during assembly.
3. Whether the mere *existence* of authorization-restricted,
   conflict-relevant, or omitted content may be disclosed to an
   unauthorized identity is not decided by this standard — it depends
   on the same unresolved question raised in
   [MAK-0004 §11](MAK-0004.md#11-security), and MAK-0002 MUST follow
   whatever that standard (or its successor access-control standard)
   ultimately decides rather than defining its own answer (see Open
   Questions).
4. Pending that decision, this standard sets a default: when an item
   is excluded because the requesting identity is not authorized to
   access it, that exclusion MUST NOT be surfaced to the requesting
   identity through the package's consumer-visible omission-reporting
   mechanism (§12) — including through a `reason` value that
   identifies or implies the exclusion was authorization-related.
   Such exclusions MAY be recorded separately, for internal audit
   purposes, outside the context package delivered to the requesting
   identity. This default is fail-closed, consistent with the
   fail-closed posture in Failure/Escalation Behavior, and applies
   only until a future access-control/existence-disclosure standard
   defines conditions under which authorization-caused omissions may
   become consumer-visible (see Open Questions, D-004).

---

### §10 Deterministic and Reproducible Assembly

1. Given identical resolved input, an identical size budget, and
   identical ordering rules, context package construction SHOULD be
   reproducible: an equivalent package (same included items, same
   ordering, same rationale) SHOULD result.
2. Byte-for-byte identity is not required; equivalence of *content
   selection, ordering, and recorded rationale* is what SHOULD be
   reproducible.
3. Any assembly step that is inherently non-deterministic (for
   example, similarity-based deduplication using a model that is not
   itself deterministic) MUST be explicitly declared as such in the
   package rather than presented as though the selection were
   rule-based.

---

### §11 Handling Unavailable Referenced Content

1. When a referenced item (§5) cannot be resolved at the time it is
   needed — because it is offline, deleted, access has been revoked,
   or the source is unreachable — this MUST NOT be treated as though
   the reference had resolved successfully.
2. Unavailability MUST be recorded on the affected item. It SHOULD be
   surfaced to the consuming AI system or requesting identity, not
   only logged internally.
3. MAK-0002 does not define retry, caching, or fallback-resolution
   mechanics for unavailable references (transport- and
   storage-neutral, per Non-Goals) — only that unavailability must be
   representable and recorded when it occurs.

---

### §12 Handling Partial Context

1. A context package MUST be able to declare that it is partial —
   that some applicable information could not be resolved, retrieved,
   or fit within the size budget.
2. A partial package MUST identify *which* categories (§1) are
   known-incomplete. This MUST be distinguishable from a category that
   is empty because nothing applicable exists for it.
3. A package that is not declared partial is asserting completeness
   relative to what was resolved and handed to it — not relative to
   all information that could theoretically exist. Completeness is
   scoped to MAK-0002's input, not to omniscience about the project.
4. Partiality alone MUST NOT be equated with unusability, and a
   partial package MAY still be produced and returned where
   appropriate. However, when information that was necessary for the
   task to be attempted correctly or safely is unavailable, unresolved,
   or excluded, the package MUST be capable of declaring context
   **insufficient for the task**, as a condition distinct from
   ordinary partiality (see Terminology). This standard does not
   define a fixed vocabulary for what counts as "necessary for the
   task" — that determination depends on priority/criticality
   information which is itself an open question (§3) — only that,
   whenever such a determination has been made upstream, MAK-0002's
   data model MUST be able to carry it through to the consuming
   system rather than silently presenting an insufficient package as
   an ordinary, usable one.
5. Authorization-caused exclusions are governed by §9.4, not by this
   section: by default they MUST NOT be surfaced through the
   omissions mechanism described above. A package MAY therefore be
   less than fully complete for authorization reasons without that
   specific reason being visible in `omissions`.

---

### §13 Declaring Inclusion Rationale

1. Each context item SHOULD carry a brief, structured inclusion
   rationale explaining why it is present (e.g., which category it
   satisfies, or what relevance signal from MAK-0003 selected it).
2. This rationale is provenance-of-selection: MAK-0002 records the
   reason it was handed by the upstream relevance/authorization
   process. It MUST NOT compute or infer a new justification of its
   own.
3. The canonical vocabulary for rationale codes is not defined by this
   standard and SHOULD be coordinated with [MAK-0003](MAK-0003.md)
   once that standard is drafted, since rationale codes are expected
   to mirror MAK-0003's relevance-signal vocabulary. This decision
   (D-005) is intentionally left unresolved until then (see Open
   Questions).

---

### §14 Context Package Version

1. Every context package MUST declare a package version identifying
   which version of the MAK-0002 data model (§15) it conforms to.
2. The package version MUST use semantic versioning, consistent with
   [MAK-0001](MAK-0001.md)'s convention, and MUST NOT be conflated
   with the version of any artifact the package contains.
3. A package SHOULD also carry an assembly-time identifier (e.g., a
   generation timestamp or id) distinct from the package version, so
   two packages built to the same schema version can still be told
   apart. Whether these are the same field or two fields is an open
   question (see Open Questions).

## Context Package Data Model (Proposed)

The following describes the conceptual fields a conformant context
package MUST be able to represent. **Serialization format is
explicitly not mandated** — JSON is used below purely for readability,
the same way MAK-0001 uses it. An implementation MAY serialize this
model as JSON, Protocol Buffers, XML, or any other format, provided
the conceptual fields and their MUST/SHOULD behavior are preserved.
Fields marked `(extension)` are not required by this draft but
illustrate how an implementation extends the model without waiting for
a new MAK-0002 version.

```json
{
  "package_version": "0.1.0",
  "generated_at": "2026-09-16T18:04:00Z",
  "requesting_identity_ref": "string | null",
  "task_ref": "string | null",
  "completeness": "complete | partial",
  "task_sufficiency": "sufficient | insufficient | unknown",
  "omissions": [
    {
      "category": "one of the §1 categories",
      "reason": "not_resolved | truncated | unavailable | other",
      "detail": "string"
    }
  ],
  "items": [
    {
      "item_id": "string",
      "category": "one of the §1 categories",
      "status": "current | historical",
      "priority": "implementation-defined, see §3 Open Questions",
      "inclusion_mode": "embedded | reference",
      "content": "string | object | null (present when inclusion_mode = embedded)",
      "reference": {
        "locator": "string (implementation-defined identifier/URI)",
        "resolvable_at_assembly": true
      },
      "inclusion_rationale": {
        "source": "mak-0003 | mak-0004 | task-scoped | other",
        "reason": "string"
      },
      "provenance": {
        "source_artifact_id": "string | null",
        "source_artifact_version": "string | null",
        "author": "string | null",
        "created_at": "ISO 8601 | null",
        "updated_at": "ISO 8601 | null"
      },
      "supersession": {
        "supersedes": "artifact-id | null",
        "superseded_by": "artifact-id | null"
      },
      "size_cost": "number | null",
      "size_cost_unit": "implementation-defined, see §6 Open Questions",
      "truncated": false,
      "unavailable": false
    }
  ]
}
```

Notes:

- `omissions` (§12) and per-item `truncated`/`unavailable` flags (§7,
  §11) together give a consuming system a picture of what is *not* in
  the package for ordinary (non-authorization) reasons.
  Authorization-caused exclusions are deliberately kept out of this
  mechanism by default (§9.4) — see the next note.
- The `reason` enum on `omissions` intentionally has no
  authorization-specific value. An exclusion caused by lack of
  authorization MUST NOT be surfaced through this field, or through
  any other consumer-visible field, unless a future access-control /
  existence-disclosure standard permits it (§9.4). Such exclusions MAY
  be recorded internally, outside the package, for audit purposes —
  that internal record is not part of this data model.
- `task_sufficiency` is a distinct axis from `completeness`:
  `completeness` describes whether all resolved, applicable
  information was included; `task_sufficiency` describes whether what
  *is* included is enough to attempt the task correctly and safely
  (§12.4). A package can be `partial` yet `sufficient`, or nominally
  `complete` yet `insufficient` if a necessary item was unavailable,
  unresolved, or excluded.
- `inclusion_rationale` (§13) and `provenance` (§8) are deliberately
  separate: provenance says where the content came from; rationale
  says why the assembler included it.
- `supersession` lets a current item point at what it replaced, or a
  historical item point at what replaced it, without requiring the
  other side to be embedded (§4.4).

## Examples

*Illustrative and non-normative. They show one valid shape a
conformant package MAY take, not the only one.*

### A. Coding task

Task: "Add rate limiting to the checkout service's public endpoints."

The package includes: project identity (current); current project
state describing the checkout service's existing architecture
(current, embedded — it's small); an active constraint ("all public
endpoints require auth middleware before rate limiting," current,
embedded); a relevant artifact — a reusable rate-limiting pattern
artifact — included as a **reference** because it's long and reused
across projects; task-specific context (the ticket description,
embedded). No historical items are included by default (§4.3), since
the task doesn't ask "why."

### B. Architecture/design task

Task: "Propose the auth model for a new multi-tenant service."

The package weights differently than (A): active decisions and their
rationale are embedded at high priority (an architecture task depends
on *why* past choices were made, not just what they are), applicable
standards/policies are embedded (e.g., an org-level tenancy-isolation
requirement), and artifact relationships are included to show how the
proposed service relates to existing services. Code-pattern artifacts
are referenced, not embedded — they're supporting material here, not
the point of the task.

### C. Continuation of work by another AI

Task: "Pick up where the previous session left off."

The package leans heavily on current project state, active decisions
with rationale, and relevant history — enough that the new AI session
does not need to ask questions already answered (per
[MAK-0004 §9](MAK-0004.md#9-decision-continuity)). Provenance on each
decision item records which prior session or identity produced it.
Supersession information is included so the new session knows a
decision changed, even where the earlier, now-historical version is
only referenced rather than embedded.

### D. Small context package

Task: a narrow, self-contained question with almost no project
dependency.

The package contains only: project identity, task-specific context,
and `completeness: complete`. Every other §1 category is legitimately
empty — not omitted (§12.2) — because nothing applicable was resolved
for them. This demonstrates that a minimal, mostly-empty package is a
valid, conformant package, not a degraded one.

### E. Context package with references to large artifacts

Task: a task where the relevant background is a large design document
and an extensive prior decision log.

Both are included as `reference` items with `resolvable_at_assembly:
true` and a locator, rather than embedded — keeping the package small
while still making the AI system aware the content exists and how to
retrieve it, consistent with §5.2's requirement that referencing is a
first-class outcome. A third reference, to an artifact whose store was
unreachable during assembly, is marked `unavailable: true` per §11.

### F. Superseded decision excluded from current context, available as history

Prior decision: "Use Platform A for new API onboarding" — superseded
in favor of "Use Platform B" (per the MAK-0004 §9 example).

The current package includes the **active** decision ("Platform B"),
embedded, `status: current`. It does **not** embed the superseded
Platform A decision by default (§4.3). Instead, it includes a
`supersession` reference on the active item pointing at the superseded
artifact's id, and (per §1) a Supersession information item recording
that the change occurred and roughly when. A consuming system that
needs the full historical rationale can resolve that reference; a
session that doesn't need it is not forced to carry the extra weight.

## Processing Behavior

```
Resolved, applicable information (MAK-0003)
                │
Conflict-resolved information (MAK-0004)
                │
                ▼
     Context Package Constructor (MAK-0002)
  ┌──────────────────────────────────────────┐
  │ 1. Categorize into §1 taxonomy            │
  │ 2. Assign status: current vs historical   │
  │ 3. Assign priority (§3)                   │
  │ 4. Decide embedded vs reference (§5)      │
  │ 5. Apply size budget; reduce/truncate (§7)│
  │ 6. Attach provenance (§8) + rationale (§13)│
  │ 7. Preserve authorization decisions (§9)  │
  │ 8. Record omissions / partial flag (§12)  │
  │ 9. Stamp package_version (§14)            │
  └──────────────────────────────────────────┘
                │
                ▼
          Context Package
                │
   (transport/injection mechanism — out of scope)
                │
                ▼
            AI Session
```

MAK-0002 defines steps 1–9. How the resulting package physically
reaches an AI system — a system prompt, an MCP resource, a tool-call
result, a file on disk — is transport-specific and explicitly out of
scope (see Non-Goals).

## Failure / Escalation Behavior

- Unavailable referenced content: recorded and surfaced, not silently
  skipped (§11).
- Size budget exceeded: defined reduction applies, with every
  reduction recorded (§7).
- Authorization cannot be determined for an item at assembly time: the
  item MUST be excluded, not included pending later determination
  (fail-closed, consistent with the fail-closed posture described in
  [ARCHITECTURE.md](../ARCHITECTURE.md#what-the-reference-implementation-ships-today)).
- Any of the above MAY cause the package to be marked partial (§12). A
  partial package MAY still be constructed and returned where
  appropriate — partiality alone is not necessarily a blocking error,
  but it is also not universally preferable to no package; whether a
  given partial package is usable depends on what, specifically, is
  missing (see below).
- When the unavailable, unresolved, or excluded information was
  necessary for the task to be attempted correctly or safely, the
  package MUST be capable of declaring context insufficient for the
  task (§12.4) — distinct from, and in addition to, marking the
  package partial. This standard does not mandate that construction
  be blocked outright in that case, only that the insufficiency MUST
  be declared rather than silently presented as an ordinary, usable
  partial package.

---

## Security Considerations

- Authorization preservation (§9) is the primary security property of
  this standard: assembly MUST NOT be a path by which restricted
  content reaches an unauthorized identity, even indirectly through
  summarization or a derived item.
- Summarized or compressed content produced during reduction (§7) MUST
  remain distinguishable from verbatim source content, so a consuming
  system (or human) cannot mistake an assembler's compression for the
  source's own words (§8.4).
- Provenance fields (§8) MUST NOT be spoofable by the content itself —
  an item's declared source/author is metadata the assembler attaches
  from the resolved input, not something read out of the content body.
- By default, MAK-0002's own omission-reporting mechanism MUST NOT be
  used to disclose that an item was excluded due to lack of
  authorization (§9.4). Whether a future access-control standard may
  permit such disclosure under defined conditions is a separate, open,
  cross-spec question shared with
  [MAK-0004 §11](MAK-0004.md#11-security) — see Open Questions, D-004.

---

## Interoperability Considerations

Because MAK4I is required to remain model-independent, vendor-
independent, cloud-independent, transport-independent, storage-
independent, and orchestration-independent, this standard defines
context-assembly *behavior*, not a wire format, SDK, or transport
binding. It MUST NOT be read as requiring MCP, A2A, any specific model
provider, any specific database or vector database, or any specific
cloud provider. Any implementation that satisfies the MUST-level
requirements in §1–§14 using a different serialization, transport, or
storage layer is equally conformant.

## Relationship to Other MAK Standards

- **[MAK-0001](MAK-0001.md)** (Artifact Metadata Schema) — MAK-0002
  reuses MAK-0001's `id`, `version`, `author`, `created_at`,
  `updated_at`, `token_estimate`, `deprecated`, and `deprecated_by` as
  its base provenance and sizing vocabulary rather than redefining
  equivalent fields.
- **[MAK-0003](MAK-0003.md)** (Memory Resolution Algorithm, planned)
  — MAK-0003 determines which information is relevant/applicable to a
  task; MAK-0002 takes that resolved output and constructs the context
  package. MAK-0002 MUST NOT perform relevance determination itself.
- **[MAK-0004](MAK-0004.md)** (Conflict Resolution Rules) — MAK-0002
  assumes conflicting applicable artifacts have already been resolved
  per MAK-0004 before assembly begins; it does not re-resolve
  conflicts. MAK-0002 also depends on MAK-0004's eventual answer to
  the existence-disclosure question in
  [MAK-0004 §11](MAK-0004.md#11-security) rather than defining its
  own (§9.3) — in the interim, MAK-0002's own omissions mechanism
  defaults to non-disclosure of authorization-caused exclusions
  (§9.4).
- **[MAK-0005](MAK-0005.md)** (Versioning and Compatibility) —
  MAK-0002 consumes lifecycle state (current/historical, superseded)
  from MAK-0005 rather than redefining lifecycle or supersession
  mechanics (§4.5).
- A future access-control standard — MAK-0002 preserves authorization
  decisions made by that standard (§9) rather than defining access
  control itself.

---

## Backward / Forward Compatibility

This is a first draft with no prior published version of MAK-0002 to
maintain compatibility against. Going forward, the `package_version`
field (§14) is the compatibility surface: a MAJOR bump indicates a
breaking change to the data model in this document, a MINOR bump adds
optional fields or categories, and a PATCH bump clarifies behavior
without changing the model — mirroring the versioning convention
[MAK-0001](MAK-0001.md#validation-rules) already establishes for
artifacts.

## Open Questions

1. What is the canonical priority-tier vocabulary for context items
   (§3), and should it be a fixed named set, an open numeric rank, or
   a hybrid? **Blocked on MAK-0003** (see D-001) — intentionally left
   unresolved until that standard is drafted.
2. What unit should context size budgets be expressed in, given that
   MAK-0002 must remain tokenizer/model neutral (§6)?
3. Should the specific truncation/reduction algorithm *within* a
   priority tier be standardized, or remain fully
   implementation-defined as proposed in §7.5?
4. MAK-0002's own omissions mechanism now defaults to non-disclosure
   of authorization-caused exclusions (§9.4). What remains open is
   whether a future access-control/existence-disclosure standard
   should define conditions under which such exclusions become
   consumer-visible, and if so, what that override mechanism looks
   like (see MAK-0004 §11, D-004)?
5. What is the canonical vocabulary for `inclusion_rationale.reason`
   (§13)? **Blocked on MAK-0003** (see D-005) — intentionally left
   unresolved until that standard is drafted, since rationale codes
   are expected to mirror its relevance-signal vocabulary.
6. Should package version (schema) and assembly-time generation
   identifier (§14.3) be a single field or two distinct fields in the
   data model?
7. Is reproducibility (§10) a MUST once real-world assembly
   implementations are evaluated, or does it need to remain a SHOULD
   because some legitimate assembly steps are inherently
   non-deterministic?
8. Should this standard eventually recommend a default serialization
   format for interoperability testing, while remaining
   format-agnostic normatively — and if so, which?
9. What determines whether a given unavailable, unresolved, or
   excluded item counts as "necessary for correct or safe task
   execution" for the purposes of declaring context insufficient
   (§12.4)? This is left open rather than answered here, since it
   likely depends on the priority vocabulary in §3, which is itself
   unresolved.

Discuss via [GitHub Issues](https://github.com/talvikai/mak4i-protocol/issues).

## Conformance Requirements

A context package is **MAK-0002 conformant** when it:

1. Is structurally capable of representing every category in §1, even
   when many are empty.
2. Declares a `package_version` (§14).
3. Marks every item's status as current or historical (§4) and
   inclusion mode as embedded or reference (§5).
4. Respects declared priority ordering during any reduction (§3, §7).
5. Preserves provenance (§8) and authorization decisions (§9) for
   every included item, and for every recorded omission.
6. Declares `completeness` and, when partial, which categories are
   known-incomplete (§12).
7. Does not present truncated, summarized, or omitted content as
   though it were complete, verbatim source content (§7, §8.4).
8. Does not use the omissions mechanism to disclose, by default, that
   an item was excluded due to lack of authorization — including
   through a reason value that identifies or implies an
   authorization-related cause (§9.4).
9. Is capable of declaring context insufficient for the task,
   distinct from ordinary partiality, when information necessary for
   correct or safe task execution is unavailable, unresolved, or
   excluded (§12.4).

Certification-level integration (how MAK-0002 conformance fits into
the broader levels described in
[CONFORMANCE.md](../CONFORMANCE.md#certification-levels)) is expected
once a conformance test suite exists for this standard; none is
published yet.

## Future Considerations

- Multi-package composition for multi-agent handoff scenarios —
  explicitly out of scope here (Non-Goals: agent orchestration,
  agent-to-agent transport) but likely to interact with this data
  model in a future standard.
- Streaming or incremental context assembly for very large projects,
  where constructing a complete package upfront may not be practical.
- A standardized, tokenizer-independent size-cost unit (§6 Open
  Question), once enough real-world implementation data exists to
  design one well.
- Whether a canonical priority-tier vocabulary (§3 Open Question)
  should be informed by usage data from early implementations rather
  than decided speculatively.
