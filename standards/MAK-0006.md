## Abstract

This standard defines who can act in a MAK4I system and what they may do:
organizations, projects, principals (human, service and agent), the
agent identifier `agent_id`, project grants and permissions, credentials,
how authenticated identity is bound to every request, how identity is
recorded in provenance, and the minimum administration and audit
semantics. Transport-specific authentication — the MCP binding and its
OAuth profile — is defined in [MAK-0008](MAK-0008.md) and MUST NOT widen
anything this standard grants.

## Motivation

MAK4I's purpose is that knowledge written by one AI client is usable by
another. That only works if every reader can trust *who* wrote a record
and every write is limited to what its author was allowed to do.
Without a shared identity and authorization contract, implementations
would differ on whether an agent can claim another agent's name, whether
an OAuth token can exceed a project grant, or whether a deactivated
principal's history stays attributable.

## Scope

In scope: the identity entities and their lifecycle; `agent_id`;
permissions and grants; credential semantics; authenticated binding;
provenance attribution; administration and its audit trail.

## Non-Goals

- Transport bindings, OAuth endpoints and token formats ([MAK-0008](MAK-0008.md)).
- Conflict and versioning semantics ([MAK-0004](MAK-0004.md), [MAK-0005](MAK-0005.md)).
- Multi-organization membership for one principal, teams, role
  hierarchies, SCIM/directory synchronization and external identity
  providers (SSO). An implementation MAY map an external identity to a
  principal (§9) but this standard supplies no connector.
- Artifact-level (finer than project) access control. Reserved for a
  future revision; see §5.4.

## Terminology

| Term | Definition |
|------|-----------|
| **Organization** | The tenancy boundary. Every principal and project belongs to exactly one organization. |
| **Project** | A container for governed records inside one organization. The unit of authorization. |
| **Principal** | An identity that can authenticate and act: a human, a service, or an agent. |
| **Agent** | A principal of type `agent`: an autonomous or semi-autonomous software actor that is administered as its own identity, separate from any human who operates it. |
| **`agent_id`** | The stable, organization-scoped identifier of an agent principal (§3). |
| **Grant** | The binding of one principal to one project with a set of permissions. |
| **Credential** | A secret issued to a principal that authenticates it (for example a bearer token). |
| **Authenticated principal** | The principal the server derived from a verified credential or a verified access token for the current request. |
| **Effective permissions** | The permissions actually usable for a request (§5.3). |
| **Instance operator** | Whoever controls the implementation's deployment and storage. Not a principal; outside this standard's authorization model (§8.1). |

## Normative Requirements

### §1 Organizations

1.1 An organization MUST have a stable identifier `organization_id`, a
`name`, and a `status` of `active` or `suspended`.

1.2 While an organization is `suspended`, every principal in it MUST be
treated as unable to authenticate, and every project in it as
inaccessible. Suspension MUST NOT delete or alter any record.

### §2 Principals

2.1 A principal MUST have:

| Field | Type | Rule |
|---|---|---|
| `principal_id` | string | Stable, unique within the implementation, never reused. |
| `organization_id` | string | Exactly one organization. Immutable. |
| `principal_type` | `human` \| `service` \| `agent` | Immutable after creation. |
| `role` | `owner` \| `member` | Organization role (§8). |
| `display_name` | string | Non-empty. Mutable (§2.4). Not an identifier. |
| `status` | `active` \| `deactivated` | §2.3. |
| `agent_id` | string | REQUIRED when `principal_type` is `agent`; MUST be absent otherwise (§3). |

2.2 Implementations that already expose the principal type under the
name `type` MAY continue to emit `type` alongside `principal_type` for
compatibility. `principal_type` is canonical; when both are present they
MUST be equal.

2.3 **Deactivation.** A deactivated principal MUST NOT authenticate by
any method, and every outstanding credential and OAuth authorization of
that principal MUST stop working no later than the next request (§6).
Deactivation MUST NOT delete the principal or alter any record it
authored. Reactivation MAY be supported; it restores the ability to
authenticate with credentials that were not individually revoked, but
MUST NOT restore OAuth authorizations that were revoked by the
deactivation (§6.3). An implementation MUST refuse to deactivate the
last active `owner` of an organization.

2.4 **Rename.** Changing `display_name` MUST NOT change `principal_id`
or `agent_id`, and MUST NOT rewrite provenance already recorded (§7).

2.5 There is no implicit principal. A request that does not carry a
verified credential or access token is unauthenticated (§4).

### §3 Agent identity (`agent_id`)

3.1 **Name.** The canonical field is `agent_id`. Implementations MUST NOT
use another name (for example `bot_id`) in new interfaces. An
implementation that previously shipped such a name MAY accept it as a
documented, deprecated alias on input only; outputs MUST use `agent_id`.

3.2 **Format.** `agent_id` MUST match
`^[a-z0-9](?:[a-z0-9._-]{1,62}[a-z0-9])$` (3–64 characters, lowercase
ASCII letters, digits, `.`, `_`, `-`, beginning and ending with a letter
or digit). It is compared byte-for-byte.

3.3 **Scope and uniqueness.** `agent_id` MUST be unique within its
organization across all agent principals, active or deactivated. The
same `agent_id` MAY exist in two different organizations; such agents
are unrelated. An `agent_id` MUST NOT be reassigned to another principal,
even after the original is deactivated.

3.4 **Lifecycle.** `agent_id` is assigned when the agent principal is
created, by an actor permitted to administer principals (§8), and is
immutable for the life of the principal. An agent is renamed by changing
`display_name` only. Deactivating an agent follows §2.3; its `agent_id`
stays reserved.

3.5 **Humans and services.** Human and service principals have no
`agent_id`. A human using an AI client (an LLM application, an IDE
assistant) acts as that human: the client is attributed as *client
metadata* (§7.3), not as an agent. An implementation MUST NOT create an
agent principal implicitly because a client connected, registered an
OAuth client, or reported a name.

3.6 **Authenticated binding.** For every request the implementation MUST
determine the acting principal solely from the verified credential or
access token (§4), and MUST take `agent_id` (if any) from that stored
principal. A value of `agent_id`, author, actor, `created_by` or any
equivalent supplied in the request body or tool arguments MUST NOT
determine identity, authorization or recorded authorship.

3.7 **Spoofing behavior.** If a request carries an explicit identity
claim (for example an `agent_id` or `principal_id` argument on an
interface that accepts one for confirmation) that differs from the
authenticated principal, the implementation MUST reject the whole
request with error `identity_mismatch` ([MAK-0008 §9](MAK-0008.md#9-error-model))
and MUST NOT perform any part of it. An equal claim MAY be accepted.
Interfaces SHOULD NOT accept such claims at all.

3.8 **OAuth clients are not agents.** An OAuth `client_id`, client name,
MCP `clientInfo`, or HTTP `User-Agent` MUST NOT be treated as, or mapped
to, an `agent_id`. An agent principal authenticates with its own
credential, or through an OAuth authorization in which the agent
principal itself is the resource owner ([MAK-0008 §5.3](MAK-0008.md#53-resource-owner-authentication)).

### §4 Authentication (abstract)

4.1 Every request to a protected interface MUST be authenticated as
exactly one principal, or rejected. Implementations MUST NOT fall back
to another identity (an anonymous user, a default principal, an operator
identity) when presented authentication is missing, malformed, invalid,
expired or revoked.

4.2 Authentication MUST verify, at the time of each request: the
credential or token is known, unrevoked and unexpired; its principal is
`active`; the principal's organization is `active`.

4.3 Transport bindings define concrete methods. [MAK-0008](MAK-0008.md)
defines bearer credentials and OAuth access tokens for MCP over HTTP and
environment-provided credentials for stdio.

### §5 Permissions and grants

5.1 **Permissions.** A grant carries a non-empty subset of:

| Permission | Allows |
|---|---|
| `read` | Discovering, retrieving and searching records of the project, viewing history and conflicts. |
| `write` | Creating and superseding records of the project. |
| `resolve` | Resolving conflicts in the project ([MAK-0004 §A7](MAK-0004.md#a7-resolution)). |

Permissions are independent: `write` does not imply `read`, and
`resolve` does not imply `read` or `write`. An operation that returns
record content additionally requires `read`. Resolving a conflict
therefore requires both `resolve` and `read`.

5.2 **Grants.** A grant binds one principal to one project with a set
of permissions. At most one grant exists per (principal, project). A
grant MUST NOT bind a principal to a project of another organization.

5.3 **Effective permissions.** For a request by authenticated principal
*P* on project *J*, the effective permissions are:

```
effective(P, J) = grant(P, J).permissions          -- live, read per request
                ∩ ceiling(authentication method)    -- e.g. OAuth scopes, MAK-0008 §7
                if  P.status = active
                and J.status = active
                and J.organization_id = P.organization_id
                and organization(P).status = active
                else ∅
```

Transport-level scopes, client registrations and consent decisions are
ceilings only; they MUST NOT add a permission that the live grant does
not contain.

5.4 Project grants are the only authorization unit in this revision.
Every principal with `read` on a project can read every record in it.
Finer-grained (per-record) restrictions are reserved; specifications
that must not leak restricted records (for example
[MAK-0004 §A6.4](MAK-0004.md#a6-retrieval-of-conflicted-subjects)) are
written so that they remain correct when such restrictions are added.

5.5 **Denials.** A request denied for lack of permission MUST fail
without effect. The response MUST NOT reveal whether the project exists
to a principal with no grant on it.

### §6 Credentials and revocation policy

6.1 A credential belongs to exactly one principal, has a `status` of
`active` or `revoked`, and MAY have an expiry. Its secret MUST be shown
only once, at issuance, and MUST be stored only in a form from which it
cannot be recovered (for example a cryptographic hash). Secrets MUST NOT
appear in list or show output, URLs or logs.

6.2 Revoking a credential MUST take effect no later than the next
request that presents it.

6.3 **Revocation policy.** Implementations MUST enforce all of the
following, evaluated on every request (no caching that outlives a
request):

| Event | Effect |
|---|---|
| Credential revoked or expired | That credential fails authentication. |
| OAuth authorization revoked | All access and refresh tokens of that authorization fail ([MAK-0008 §6](MAK-0008.md#6-tokens)). |
| Principal deactivated | Every credential and token of the principal fails; every OAuth authorization of the principal is revoked. |
| Organization suspended | Every principal of the organization fails authentication. |
| Grant removed or reduced | Effective permissions shrink on the next request. |
| Project archived | Effective permissions on it become ∅. |

6.4 A long-lived connection (for example a stdio process) MUST re-check
§4.2 before each operation or terminate when the check would fail.

### §7 Provenance

7.1 Every version of a governed record ([MAK-0005 §A2](MAK-0005.md#a2-record-fields))
MUST carry authenticated provenance recorded by the server at write
time, conforming to [`provenance.schema.json`](../schemas/provenance.schema.json):

| Field | Source | Notes |
|---|---|---|
| `principal_id` | authenticated principal | REQUIRED |
| `principal_type` | stored principal | REQUIRED |
| `agent_id` | stored principal | REQUIRED for agents; `null` otherwise |
| `display_name` | stored principal at write time | Snapshot; never rewritten |
| `auth_method` | how the request was authenticated | `credential`, `oauth`, or `operator` |
| `credential_id` | the credential used | when `auth_method` = `credential` |
| `oauth_client_id` | the OAuth client | when `auth_method` = `oauth` |
| `client` | client self-report | OPTIONAL, `{name, version, verified: false}` |
| `recorded_at` | server clock | REQUIRED |

7.2 `principal_id`, `principal_type`, `agent_id`, `auth_method`,
`credential_id`, `oauth_client_id` and `recorded_at` MUST be derived by
the server and MUST NOT be accepted from the request.

7.3 **Unverified client metadata.** Client-reported names (MCP
`clientInfo`, `User-Agent`, OAuth client names from dynamic registration
or metadata documents) MAY be recorded under `client` and MUST be marked
`verified: false`. Consumers MUST NOT use `client` for authorization or
to establish authorship.

7.4 Provenance is immutable. Renaming or deactivating the principal
MUST NOT alter provenance of existing versions; readers SHOULD resolve
the current `display_name` separately when they want it.

7.5 Records written before an implementation adopted this standard MAY
lack `provenance`. Implementations MUST NOT fabricate provenance for
them; they expose whatever authorship they recorded at the time (for
example a legacy `created_by` principal identifier).

7.6 `auth_method = operator` denotes an action performed by the instance
operator outside the authentication model (§8.1). It MUST still name the
principal on whose behalf the operator acted.

### §8 Administration

8.1 **Instance operator.** Bootstrap (creating the first organization
and its first owner) and recovery are performed by the instance operator
through local tooling with direct access to the implementation's
storage. Implementations MUST NOT expose an unauthenticated remote
administration endpoint, including for bootstrap.

8.2 **Organization owners.** An active principal with `role = owner` MAY,
within its own organization only: create and archive projects; create,
rename and deactivate principals (including assigning `agent_id`);
create, change and remove grants; issue and revoke credentials; manage
OAuth clients and revoke OAuth authorizations ([MAK-0008 §8](MAK-0008.md#8-administration-of-oauth)).
An owner MUST NOT act on another organization.

8.3 **Members** have no administrative rights. Holding any project
permission (including `resolve`) MUST NOT confer administrative rights
over that project, other projects, the organization or the instance.

8.4 **No destructive purge.** Administrative lifecycle operations are
deactivate, archive, suspend and revoke. This standard defines no
operation that deletes principals, projects, grants, credentials or
records.

8.5 **Audit.** Every successful or denied administrative action MUST
produce an attributable event conforming to
[`admin-event.schema.json`](../schemas/admin-event.schema.json): event id,
time, actor (principal and auth method), action, target identifiers,
outcome, and correlation id. Events MUST NOT contain secrets. The events
MUST be durably retrievable by organization owners for their
organization; implementations MAY additionally stream them to logs.

### §9 External identity adapters (non-normative guidance)

An implementation MAY let a deployment map identities from an external
system (an enterprise IdP, a custom gateway) to MAK4I principals. Such
an adapter is part of authentication only. It MUST:

- verify the external assertion cryptographically or over a trusted
  channel, and map a *stable* external subject (never a display name or
  email alone) to exactly one principal;
- never create or alter grants, roles or `agent_id` as a side effect of
  sign-in unless an owner configured that mapping explicitly;
- honor §2.3 and §6.3 for the mapped principal;
- leave §5 enforcement unchanged.

Accepting an arbitrary trusted identity header from the network is not
a conforming adapter.

## Examples

Agent principal:

```json
{
  "principal_id": "prn_7c1e…",
  "organization_id": "org_42aa…",
  "principal_type": "agent",
  "agent_id": "release-bot",
  "role": "member",
  "display_name": "Release bot",
  "status": "active"
}
```

Effective permissions: grant `{read, write}`, OAuth scopes
`mak4i:read mak4i:resolve` ⇒ effective `{read}`.

## Security Considerations

- Identity is never taken from request content (§3.6, §7.2).
- Revocation is evaluated per request (§6.3); caches that outlive a
  request would violate this standard.
- Denials do not disclose project existence (§5.5).

## Backward / Forward Compatibility

New in this revision. Implementations that predate it typically have
principals without `agent_id` and records without `provenance`: both
remain valid (§2.1 only requires `agent_id` for agents; §7.5). Adding
`resolve` to the permission set is additive.

## Conformance Requirements

An implementation conforms to MAK-0006 when it satisfies §1–§8 and its
interfaces validate against the referenced schemas. The acceptance
checklist is in [CONFORMANCE.md](../CONFORMANCE.md#mak-0006-identity-and-access-control).

## Relationship to Other MAK Standards

- [MAK-0008](MAK-0008.md) binds this model to MCP and OAuth.
- [MAK-0004](MAK-0004.md) and [MAK-0005](MAK-0005.md) use §5 permissions
  and §7 provenance.
- [MAK-0001](MAK-0001.md)'s free-text `author` field is packaging
  metadata, not authenticated provenance.
