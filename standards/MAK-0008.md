## Abstract

This standard binds MAK4I to the Model Context Protocol (MCP). It
defines the supported transports and MCP revisions, how requests are
authenticated (bearer credentials and a self-contained OAuth 2.1
authorization service), the MCP tool catalog with its permissions, and
the error model. Identity and permission semantics come from
[MAK-0006](MAK-0006.md); this binding MUST NOT define or widen them.

## Motivation

AI clients reach MAK4I mainly over MCP. Hosted clients (for example
claude.ai) can only connect to remote servers that offer OAuth; local
clients and automation use static credentials. A single binding lets
any MAK4I implementation interoperate with any MCP client in both modes
without inventing its own discovery, token or error behavior.

## Scope

Transports, MCP revision pinning, authentication methods and precedence,
the OAuth authorization-server profile (discovery, authorization with
PKCE, resource-owner sign-in and consent, tokens, refresh, revocation,
client registration), scopes, the tool catalog, errors, and the
configuration values that determine advertised URLs.

## Non-Goals

- Single sign-on with external identity providers, SCIM, administrative
  web portals. (An implementation MAY add them outside this binding; see
  [MAK-0006 §9](MAK-0006.md#9-external-identity-adapters-optional-normative-when-implemented).)
- Transport-independent REST APIs (future work).
- Token formats beyond what interoperability requires (§6.1).

| Term | Definition |
|------|-----------|
| **MCP endpoint** | The Streamable HTTP endpoint at which the implementation serves MCP. |
| **Resource identifier** | The canonical URI of the MCP endpoint, used as the OAuth resource / audience (§3). |

## Normative Requirements

### §1 Transports

1.1 **stdio.** The client launches the implementation as a local
process. The principal is authenticated from a credential supplied out
of band (for example an environment variable) before the first
operation and re-checked per [MAK-0006 §6.4](MAK-0006.md#6-credentials-and-revocation-policy).
OAuth does not apply to stdio.

1.2 **Streamable HTTP.** The implementation serves MCP at one MCP
endpoint. Every request to it MUST be authenticated (§2). Remote
deployments MUST use HTTPS; plain HTTP is permitted only on loopback
interfaces.

1.3 **Sessions.** When the transport establishes a session, the session
MUST be bound to the authenticated principal that created it. A request
on that session authenticated as a different principal MUST be rejected
(HTTP 404 or 403) without effect.

1.4 Health and readiness endpoints MAY be unauthenticated and MUST NOT
return any record, identity or configuration data.

### §2 Authentication methods and precedence (HTTP)

2.1 Two bearer token kinds are accepted in the `Authorization` header
with the `Bearer` scheme (scheme name case-insensitive):

| Kind | Issued by | Distinguishing prefix |
|---|---|---|
| Principal credential ([MAK-0006 §6](MAK-0006.md#6-credentials-and-revocation-policy)) | administration | implementation-defined, e.g. `mak4i_` |
| OAuth access token (§6) | the authorization service | implementation-defined, distinct from the above |

2.2 The two kinds MUST be distinguishable without trial verification
(for example by prefix). A presented token MUST be verified only as the
kind it claims to be. If verification fails the request MUST be rejected
with 401 `invalid_token` (§4.2); the implementation MUST NOT retry it as
the other kind or fall back to any other identity.

2.3 A request MUST be rejected with 400 `invalid_request` if it carries
more than one `Authorization` header, or a token in a URI query
parameter or form body. Tokens are accepted only in the header.

2.4 Tokens not issued by this implementation — ID tokens, upstream or
third-party access tokens, JWTs from other issuers — MUST be rejected.
The implementation MUST NOT pass any received token to another service.

2.5 A request without credentials receives 401 with the challenge in
§4.2.

### §3 Resource and issuer identifiers

3.1 The **resource identifier** is the absolute HTTPS URI (or, only for a
deployment bound to a loopback interface, the `http` URI on `127.0.0.1`,
`[::1]` or `localhost`, consistent with §1.2) of the MCP
endpoint as clients reach it (scheme, host, optional port, full path
including any reverse-proxy prefix), without query, fragment or trailing
slash. Example: `https://mak4i.example.com/team-a/mcp`.

3.2 The **issuer** is an absolute HTTPS URI without query or fragment
(or, under the same loopback-only condition as §3.1, an `http` loopback
URI). It MAY have a path. Hosted clients can only use HTTPS deployments
(see Interoperability Considerations). Example: `https://mak4i.example.com/team-a`.

3.3 Both values MUST come from deployment configuration (§12). An
implementation MUST NOT derive them from request headers (`Host`,
`X-Forwarded-*`, `Forwarded`) unless the deployment explicitly
configured the proxy as trusted, and then only from that proxy.

3.4 Every URL the implementation advertises (metadata, challenges,
endpoint locations) MUST be built from these configured values so that
it is correct behind path prefixes and reverse proxies.

### §4 Discovery

4.1 **Protected resource metadata (RFC 9728).** The implementation MUST
serve a document conforming to
[`oauth-protected-resource-metadata.schema.json`](../schemas/oauth-protected-resource-metadata.schema.json)
at the path-inserted location
`<origin>/.well-known/oauth-protected-resource<resource-path>`, and
SHOULD also serve it at `<origin>/.well-known/oauth-protected-resource`
when no other resource on the origin uses that location. It MUST contain
`resource` (equal to §3.1), `authorization_servers` (exactly the issuer),
`scopes_supported` (§7) and `bearer_methods_supported: ["header"]`. It
MUST NOT advertise `offline_access`. These documents MUST be served
without authentication.

4.2 **Challenges.** A 401 response from the MCP endpoint MUST include

```
WWW-Authenticate: Bearer resource_metadata="<PRM URL>", scope="<space-separated scopes>"
```

and, when a token was presented, `error="invalid_token"`. A request whose
token lacks a scope required by the operation MUST receive 403 with
`error="insufficient_scope"`, `scope` listing every scope the operation
requires (it MAY also list scopes the token already holds, so a client
can re-authorize for the complete set), and `resource_metadata`. This 403
is an access denial attributed to the authenticated principal
([MAK-0006 §8.6](MAK-0006.md#8-administration)). A deployment with OAuth
disabled has no protected-resource metadata; its 401 responses carry
`WWW-Authenticate: Bearer` with a `realm` and no `resource_metadata`, and
this subsection's OAuth parameters do not apply. A grant-level denial (the principal
lacks the permission on the project) is not a scope problem: it is
reported as a tool error `access_denied` (§9), not as 403.

4.3 **Authorization server metadata (RFC 8414).** The implementation
MUST serve a document conforming to
[`oauth-authorization-server-metadata.schema.json`](../schemas/oauth-authorization-server-metadata.schema.json)
at `<origin>/.well-known/oauth-authorization-server<issuer-path>` (path
insertion; no suffix when the issuer has no path). Its `issuer` MUST be
identical to §3.2. It MUST advertise: `authorization_endpoint`,
`token_endpoint`, `revocation_endpoint`, `response_types_supported:
["code"]`, `grant_types_supported: ["authorization_code",
"refresh_token"]`, `code_challenge_methods_supported: ["S256"]`,
`token_endpoint_auth_methods_supported` including `"none"`,
`scopes_supported`, and `authorization_response_iss_parameter_supported:
true` (RFC 9207). It MUST advertise
`client_id_metadata_document_supported: true` if and only if §8.3 is
enabled, and `registration_endpoint` if and only if §8.4 is enabled.
It MUST NOT advertise a mechanism it does not support.

4.4 Endpoint paths are implementation-defined; clients MUST use the
locations from metadata. Behind a reverse proxy with a path prefix, the
deployment MUST route the advertised endpoint URLs (built from §3 values)
to the implementation, including the path-inserted `/.well-known/…`
locations of §4.1 and §4.3. Implementations SHOULD document the
required proxy routes.

### §5 Authorization endpoint

#### 5.1 Request validation

The authorization endpoint MUST validate, before showing any page:

1. `client_id` identifies a registered (§8) or resolvable (§8.3) client;
2. `redirect_uri` is present and matches §5.2;
3. `response_type` is `code`;
4. `code_challenge` is present and `code_challenge_method` is `S256`;
5. `resource` is present and equals the resource identifier (§3.1);
6. every requested `scope` is in `scopes_supported`.

If (1) or (2) fails, the endpoint MUST show an error page and MUST NOT
redirect. Otherwise errors are returned to the redirect URI as in
OAuth 2.1, with `state` and `iss`. A mismatched `resource` yields
`invalid_target`.

#### 5.2 Redirect URIs

5.2.1 Redirect URIs MUST be compared to the client's registered values
by exact string match, with one exception: for a registered loopback URI
with scheme `http` and host `127.0.0.1`, `[::1]` or `localhost`,
any port is accepted when scheme, host and path match exactly (RFC 8252
§7.3).

5.2.2 Non-loopback redirect URIs MUST use `https`. Fragments and
wildcards are never accepted.

#### 5.3 Resource owner authentication

5.3.1 The resource owner is a MAK4I principal
([MAK-0006 §2](MAK-0006.md#2-principals)). The authorization service
authenticates it with a **sign-in code**:

- issued for one principal, on request of that principal or an owner of
  its organization, through local administration tooling (never by an
  unauthenticated network endpoint);
- at least 128 bits of entropy (for example a random string in a
  human-copyable alphabet), stored only as a hash;
- valid for at most 10 minutes (default 10), single use, consumed by
  the first successful sign-in;
- usable only on the sign-in page of this authorization service. It
  MUST NOT be accepted as a bearer token or at the token endpoint.

5.3.2 Implementations MUST NOT offer password authentication or accept a
principal credential ([MAK-0006 §6](MAK-0006.md#6-credentials-and-revocation-policy))
in place of the authorization-code-with-PKCE flow. (A credential is not
exchanged for tokens anywhere in this binding.)

5.3.3 A successful sign-in establishes a browser session bound to that
principal for at most 15 minutes, sufficient to complete consent.

5.3.4 An agent principal MAY be the resource owner (its operator signs
in with a sign-in code issued for the agent). The resulting tokens then
act as the agent ([MAK-0006 §3.8](MAK-0006.md#3-agent-identity-agent_id)).

#### 5.4 Consent

5.4.1 Before issuing a code, the service MUST show a consent page naming:
the signed-in principal; the client's name, labelled *unverified* unless
it was pre-registered by an owner; the redirect URI's host; the
requested scopes in plain language; and the resource. The resource owner
MUST explicitly approve. Denial redirects with `access_denied`.

5.4.2 The service MUST require consent on every authorization request
unless the client was pre-registered by an owner and the same principal
already approved the same scopes for it; remembered consent never covers
clients registered through §8.3 or §8.4.

#### 5.5 Browser security

- Session and CSRF cookies MUST be `HttpOnly`, `SameSite=Lax` or
  stricter, and `Secure` whenever the issuer is HTTPS.
- Every state-changing form (sign-in, consent) MUST carry a CSRF token
  bound to the browser session.
- Pages MUST send `Cache-Control: no-store` and forbid framing
  (`Content-Security-Policy: frame-ancestors 'none'`).
- Sign-in attempts MUST be rate-limited (§11.1).

#### 5.6 Authorization response

On approval the service redirects to the redirect URI with `code`,
`state` (if supplied) and `iss` (the issuer, RFC 9207).

### §6 Tokens

6.1 **Formats.** Authorization codes, access tokens and refresh tokens
MUST each contain at least 128 bits of entropy and MUST be stored only
as hashes. Opaque (reference) tokens are RECOMMENDED; they need no
signing keys. An implementation that issues self-contained tokens MUST
also satisfy §6.6 and §6.7 for every request, which in practice requires
a server-side revocation lookup.

6.2 **Authorization codes** are bound to client, redirect URI, PKCE
challenge, resource, granted scope and principal; expire within 60
seconds by default (at most 10 minutes); and are single use. Presenting
a code a second time MUST fail with `invalid_grant` and MUST revoke the
authorization that the code produced.

6.3 **Token endpoint, `authorization_code` grant.** The endpoint MUST
accept `application/x-www-form-urlencoded`, authenticate confidential
clients, and verify: the code is valid, unused and issued to this
client; `redirect_uri` equals the authorization request's; the PKCE
verifier matches (S256); `resource`, if present, equals the code's
resource. The response contains `access_token`, `token_type: Bearer`,
`expires_in`, `refresh_token` and the granted `scope`, with
`Cache-Control: no-store`.

6.4 **Access tokens** are bound to one authorization: principal, client,
resource (audience) and scope. Default lifetime 1 hour (configurable,
at most 24 hours).

6.5 **Refresh tokens and rotation.** Every successful use of a refresh
token (grant `refresh_token`) MUST return a new refresh token and
invalidate the presented one. Presenting an already-rotated refresh
token is **replay**: the request MUST fail with `invalid_grant` and the
whole authorization (every access and refresh token descending from it)
MUST be revoked. A refresh request MAY narrow but MUST NOT widen scope,
and MUST re-check [MAK-0006 §4.2](MAK-0006.md#4-authentication-abstract).
An authorization MUST end — requiring the resource owner to sign in and
consent again — after its **idle lifetime** (default 7 days without a
refresh) or its **absolute lifetime** (default 30 days from consent),
whichever comes first. Expired or revoked refresh tokens yield
`invalid_grant`.

6.6 **Validation at the MCP endpoint.** For every request the
implementation MUST verify that the access token exists, is unexpired
and unrevoked, belongs to an unrevoked authorization, was issued by this
issuer for **this** resource identifier, and that
[MAK-0006 §4.2](MAK-0006.md#4-authentication-abstract) holds. Effective
permissions are then computed per
[MAK-0006 §5.3](MAK-0006.md#5-permissions-and-grants) with the token's
scopes as the ceiling (§7).

6.7 **Revocation (RFC 7009).** The revocation endpoint MUST accept access
and refresh tokens. Revoking a refresh token revokes its authorization;
revoking an access token revokes at least that token. It MUST respond
200 for unknown tokens. Administrative revocation is defined in §8.5.

6.8 **Persistence.** Outstanding codes, authorizations, refresh state and
revocation state MUST be stored durably so that they behave identically
across restarts of the implementation.

### §7 Scopes

| Scope | Ceiling on permission ([MAK-0006 §5.1](MAK-0006.md#5-permissions-and-grants)) |
|---|---|
| `mak4i:read` | `read` |
| `mak4i:write` | `write` |
| `mak4i:resolve` | `resolve` |

7.1 A scope never grants a permission the live project grant lacks.

7.2 If an authorization request omits `scope`, the service grants
`mak4i:read mak4i:write` subject to consent.

7.3 Refresh tokens are issued for every authorization-code grant;
`offline_access` is neither required nor advertised.

7.4 Principal credentials have no scope ceiling: their ceiling is all
permissions.

### §8 Administration of OAuth

#### 8.1 Client registration modes

The authorization service supports one or more of the following. It
MUST advertise exactly those enabled (§4.3).

| Mode | Default | Use |
|---|---|---|
| Pre-registration (§8.2) | enabled | Clients configured with a client ID (and optionally a secret). |
| Client ID Metadata Documents (§8.3) | enabled | Clients whose `client_id` is an HTTPS URL (e.g. hosted AI clients). |
| Dynamic Client Registration (§8.4) | disabled | Compatibility with clients that support neither of the above. |

An unknown `client_id` that is not resolvable under an enabled mode MUST
be refused (§5.1).

#### 8.2 Pre-registration

An organization owner (or the instance operator) registers a client with
a display name, one or more redirect URIs (§5.2) and a client type.
Confidential clients receive a secret shown once and stored hashed.
Pre-registered clients belong to one organization and MAY only be used
by principals of that organization.

#### 8.3 Client ID Metadata Documents

When `client_id` is an `https` URL, the service fetches it as a client
metadata document and MUST:

- refuse URLs that are not `https`, contain a fragment, credentials or
  dot-segments, or resolve to loopback, private, link-local or otherwise
  non-public addresses (SSRF protection, applied to every resolved
  address);
- not follow redirects; enforce a timeout (at most 5 s) and a size limit
  (at most 64 KiB); require a JSON object;
- validate it against
  [`client-id-metadata-document.schema.json`](../schemas/client-id-metadata-document.schema.json),
  require its `client_id` to equal the URL exactly, and require
  `token_endpoint_auth_method` to be `none`;
- validate the request's redirect URI against the document's
  `redirect_uris` (§5.2);
- show the redirect host on the consent page (§5.4);
- cache documents for at most 24 hours, honoring `Cache-Control`.

A deployment MAY restrict accepted metadata-document hosts to an
allowlist.

#### 8.4 Dynamic Client Registration (optional)

If enabled, the registration endpoint MUST accept only public clients
(`token_endpoint_auth_method: none`), validate redirect URIs per §5.2,
require `authorization_code` in `grant_types`, rate-limit requests
(§11.1), and label registered names unverified (§5.4). DCR is deprecated
in MCP 2026-07-28 and is provided for compatibility only.

#### 8.5 Administrative controls

Organization owners MUST be able to, for their organization: list and
disable pre-registered clients; list OAuth authorizations by principal
or client (never showing token values); revoke one authorization, all
authorizations of a principal, or all authorizations of a client. Every
such action is audited per [MAK-0006 §8.5](MAK-0006.md#8-administration).

### §9 Error model

9.1 HTTP-level authentication errors follow §4.2. OAuth endpoints use
OAuth error codes.

9.2 Tool-level errors MUST be returned as MCP tool results with
`isError: true` whose `structuredContent` conforms to
[`error.schema.json`](../schemas/error.schema.json):
`{"error": {"code": "<code>", "message": "<text>", "retryable": <bool>}}`.
A human-readable text content block with the same message SHOULD also be
present.

| Code | Meaning | Retry? |
|---|---|---|
| `access_denied` | The principal lacks the permission, or the project does not exist (indistinguishable, [MAK-0006 §5.5](MAK-0006.md#5-permissions-and-grants)). | No — and MUST NOT be retried on another connection |
| `identity_mismatch` | An identity claim differs from the authenticated principal ([MAK-0006 §3.7](MAK-0006.md#3-agent-identity-agent_id)). | No |
| `validation_error` | Arguments violate the tool schema or a field rule. | No |
| `not_found` | A referenced record or conflict does not exist in a project the caller can read. | No |
| `artifact_exists` | A create named an `artifact_id` that already exists in the project. Nothing was written. | No |
| `artifact_not_active` | The supersede target is not the current head ([MAK-0005 §A4](MAK-0005.md#a4-supersession-and-stale-head-protection)). | No |
| `stale_head` | A concurrent write changed the head; nothing was written. | Yes, after re-reading |
| `subject_key_change` | A supersession tried to change or reclaim a subject key outside a resolution. | No |
| `subject_in_conflict` | A supersession tried to release the key of a candidate of an open conflict ([MAK-0004 §A3.7](MAK-0004.md#a3-detection)); resolve the conflict instead. | No |
| `conflict_changed` | A resolution named a candidate set that no longer matches ([MAK-0004 §A8](MAK-0004.md#a8-concurrency-idempotency-and-errors)). | Yes, after re-reading |
| `conflict_not_open` | The conflict was already resolved or no longer exists. | No |
| `subject_collision` | A separate-subjects assignment collides with another subject. | No |
| `cursor_expired` | A `mak4i_changes` cursor is older than the retained feed (§14.4); re-read current knowledge and continue from its `change_sequence`. | No |
| `rate_limited` | Too many requests. | Yes, later |
| `internal_error` | Unexpected failure; no partial effect was committed, or the operation is safely retryable. | Yes |

9.3 Error messages MUST NOT contain secrets, and denials MUST NOT reveal
whether a project or record exists to a caller without access.

9.4 `error.correlation_id` SHOULD be populated with the identifier of the
implementation's audit/security event for the request
([MAK-0006 §8.6](MAK-0006.md#8-administration)), so operators can link a client
report to server events. Clients MUST NOT parse `message`.

9.5 **Unknown codes.** Later revisions may add codes. Clients MUST treat
an unrecognized `code` according to its `retryable` flag and MUST NOT
fail because the code is unknown.

### §10 Tool catalog

10.1 Tools, their arguments and results are defined in
[`mcp-tools.schema.json`](../schemas/mcp-tools.schema.json). Required
permissions are evaluated per [MAK-0006 §5.3](MAK-0006.md#5-permissions-and-grants);
scopes per §7.

| Tool | Purpose | Requires |
|---|---|---|
| `mak4i_whoami` | Connection identity, organization, authenticated principal (incl. `agent_id`), auth method | authentication |
| `mak4i_list_projects` | Projects the principal holds any permission on, with its effective permissions | authentication |
| `mak4i_search` | Deterministic lookup by type / tags / status | `read` |
| `mak4i_get_current` | Current authoritative records plus conflicted subjects ([MAK-0004 §A6](MAK-0004.md#a6-retrieval-of-conflicted-subjects)) | `read` |
| `mak4i_create` | Create a record (new lineage) | `write` |
| `mak4i_supersede` | Create the next version of a lineage | `write` |
| `mak4i_history` | All versions of a lineage | `read` |
| `mak4i_list_conflicts` | Open (and optionally resolved) conflicts | `read` |
| `mak4i_get_conflict` | One conflict with its candidates and resolution | `read` |
| `mak4i_resolve_conflict` | Resolve a conflict ([MAK-0004 §A7](MAK-0004.md#a7-resolution)) | `read` + `resolve` |
| `mak4i_changes` | The project's change feed after a cursor (§14.4); **only** in the optional `server-change-feed` profile | `read` |

10.2 Tools MUST NOT accept arguments that set identity or provenance
([MAK-0006 §7.2](MAK-0006.md#7-provenance)). Tool inputs are closed: an
argument not defined for the tool in
[`mcp-tools.schema.json`](../schemas/mcp-tools.schema.json) MUST be
rejected with `validation_error`. An explicit identity claim
(`agent_id`, `principal_id`, `created_by`, …) that differs from the
authenticated principal MUST be rejected with `identity_mismatch`
([MAK-0006 §3.7](MAK-0006.md#3-agent-identity-agent_id)), and either rejection is a
refused-write security event for write tools
([MAK-0006 §8.6](MAK-0006.md#8-administration)). Implementations SHOULD
advertise the same constraints (enums, patterns, closed objects) in the
MCP `inputSchema` of each tool.

10.3 Equivalent operations MAY be exposed through other interfaces (for
example a CLI). Such interfaces MUST apply the same authorization and
produce the same records and errors. An implementation SHOULD document
the mapping between tool names and its other interface commands.

10.4 Implementations MAY add tools. Added tools MUST NOT use the
`mak4i_` prefix; that prefix is reserved for tools this standard
defines. Implementation-specific result fields follow the extensibility
rules in [SPEC.md](../SPEC.md#extensibility).

10.5 **Result shape.** A successful tool result carries its data in
`structuredContent`, which MCP requires to be a JSON object. Tools whose
result is a list (`mak4i_list_projects`, `mak4i_search`, `mak4i_history`,
`mak4i_list_conflicts`) therefore return `{"result": [ … ]}`. In
`mak4i_whoami`, `scopes` is the access token's scope list for OAuth and
`null` for a principal credential (which has no scope ceiling, §7.4); the
key is always present. `mak4i_whoami.protocol` reports the protocol
release the implementation targets (`version`) and the conformance
profiles it claims (`profiles`, [CONFORMANCE.md](../CONFORMANCE.md#conformance-profiles));
clients use it for compatibility checks (§13.8).

10.5a **Further result rules.**
- `mak4i_search` and `mak4i_get_current` tag filters match records that
  carry **all** listed tags.
- `mak4i_search` without `status` returns `active` versions; a `status`
  outside the defined values is a `validation_error`.
- On `mak4i_supersede` the successor's `artifact_id` is assigned by the
  server and opaque; clients read it from the result. Supplying both a
  different `subject_key` and `release_subject_key: true` fails with
  `subject_key_change`, and so does releasing on a lineage that has no
  key.
- `mak4i_get_current` results MAY carry `resolution_trace_id` /
  `resolution_trace`: an opaque, implementation-defined explanation that
  clients MUST NOT parse.
- `mak4i_whoami.connection` (instance name, environment, public endpoint,
  server version) and `mak4i_list_projects[].organization_name` are
  informational.

10.6 **Discovery defaults.** Withdrawn and superseded versions are never
current knowledge:

| Tool | Default | Withdrawn / superseded versions |
|---|---|---|
| `mak4i_get_current` | current records plus conflicts | never returned as current records (a candidate of an open or resolving conflict appears only inside `conflicts`) |
| `mak4i_search` | `status = "active"` | returned only when `status` is explicitly `"withdrawn"` or `"superseded"` |
| `mak4i_history` | every version of the lineage, oldest first | always included, with their status and `resolution_id` |
| `mak4i_list_conflicts` | `state = "open"` (includes `resolving`) | resolved conflicts (with withdrawn candidates and their resolution record) only with `state = "resolved"` or `"all"` |
| `mak4i_get_conflict` | the conflict in its current state | a resolved conflict includes its withdrawn candidates |

Context assembly for injection ([MAK-0002](MAK-0002.md), Draft in progress) is out of scope here;
until it is complete, implementations MUST NOT inject withdrawn or superseded
versions as current knowledge.

10.7 **No binding for MAK-0009 yet (approved future scope).**
- This revision defines no tools, arguments, result fields or error codes
  for distributable artifacts, resources, resource groups, rules or
  effective rules ([MAK-0009 §8](MAK-0009.md#8-conformance-status-at-this-revision)).
- Tools MUST NOT accept or emit the architecture-defined record fields
  `resource_id` and `rule` until that binding exists. The binding, error
  codes and conformance criteria are written in the milestone that
  implements MAK-0009 ([MAK-0009 §8.4](MAK-0009.md#8-conformance-status-at-this-revision)).

### §11 Operational security

11.1 **Rate limiting.** Sign-in, token, revocation and registration
endpoints MUST be rate-limited per client address and SHOULD be
rate-limited per client and principal; exceeding a limit yields HTTP 429
(OAuth endpoints) or `rate_limited` (tools). Defaults are
implementation-defined and documented.

11.2 **Logging.** Implementations MUST NOT log or include in errors:
credentials, sign-in codes, authorization codes, access or refresh
tokens, client secrets, or private keys. Request URLs that carry an
authorization code (the redirect) are never logged by the service
itself.

11.3 **Keys.** If an implementation uses signing or encryption keys
(for example for self-contained tokens or cookies), it MUST persist
them outside source control and configuration files (for example in its
protected data store or a secret reference), document their rotation,
and continue to accept tokens and sessions signed with a previous key
until they expire. An implementation using only opaque tokens and
server-side sessions needs no long-lived keys.

### §12 Configuration contract

An implementation's configuration MUST be able to express, and MUST
validate at startup:

| Setting | Meaning |
|---|---|
| Deployment mode | e.g. local, self-hosted |
| Resource identifier | §3.1 (REQUIRED when OAuth is enabled) |
| Issuer | §3.2 (REQUIRED when OAuth is enabled) |
| Enabled authentication methods | principal credentials, OAuth |
| Enabled registration modes | §8.1 |
| Token policy | code, access-token, refresh idle/absolute lifetimes; sign-in-code lifetime |
| Proxy trust | which proxies (if any) may supply forwarded headers (§3.3) |
| Rate limits | §11.1 |

Secrets MUST be supplied by reference (environment, file, secret store),
never inline in configuration files committed to source control.

### §13 Client requirements

This section binds MAK4I **clients**: SDKs, agents and integrations that
call the tools. §1–§12 bind servers.

13.1 **Transport.** A client MUST connect over a transport in §1. Over HTTP
it MUST use HTTPS, except to a loopback host. It MUST send the
`MCP-Protocol-Version` negotiated at initialization and MUST support at
least one handshake revision listed under "Pinned external
specifications".

13.2 **Credentials.**
- A client MUST send a token only in the `Authorization: Bearer` header,
  and only to the origin of the resource identifier it was issued for.
- It MUST NOT place tokens in URLs, logs, error messages or exception
  text.
- A principal credential MUST be obtained out of band (configuration,
  environment or file) and is never exchanged for OAuth tokens (§5.3.2).

13.3 **OAuth discovery and authorization.** A client using OAuth MUST:
- (a) discover the authorization server from the 401 `resource_metadata`
  (RFC 9728), then the server metadata (RFC 8414, path-inserted);
- (b) use authorization code + PKCE S256 only;
- (c) send `resource` equal to the resource identifier on authorization
  and token requests (RFC 8707);
- (d) verify that `iss` in the authorization response equals the issuer
  (RFC 9207), and verify `state`;
- (e) use a redirect URI registered for its client id; a native client
  SHOULD use a loopback redirect (RFC 8252 §7.3);
- (f) not use Dynamic Client Registration when pre-registration or a
  Client ID Metadata Document is available.

13.4 **Token lifecycle.**
- On every refresh, a client MUST replace the stored refresh token with
  the new one atomically, and MUST NOT present a rotated refresh token
  again (§6.5).
- On `invalid_grant` it MUST discard its tokens and re-authorize.
- On 403 `insufficient_scope` it MAY re-authorize for the listed scopes;
  scopes never widen the principal's grant
  ([MAK-0006 §5.3](MAK-0006.md#5-permissions-and-grants)).
- Stored tokens MUST be protected from other local users.

13.5 **Results.**
- A client MUST read results from `structuredContent` and unwrap
  `{"result": [...]}` for list tools (§10.5).
- It MUST ignore output fields it does not recognize
  ([SPEC.md](../SPEC.md#extensibility)).
- It MUST NOT treat withdrawn or superseded versions as current (§10.6).

13.6 **Errors and retries.**
- A client MUST classify tool errors by `error.code`, never by message
  text, and MUST handle unknown codes per §9.5.
- It MUST NOT retry a non-retryable error unchanged.
- It MUST re-read state before retrying `stale_head` or `conflict_changed`.
- After `access_denied` it MUST NOT retry the operation through another
  connection or identity (§9).

13.7 **Writes.**
- A client MUST NOT send identity or provenance arguments (§10.2).
- For `mak4i_resolve_conflict` it SHOULD send an `idempotency_key` (8–200
  characters) and MUST reuse the same key and parameters when retrying.
- It MUST name the exact candidate set it read
  ([MAK-0004 §A8](MAK-0004.md#a8-concurrency-idempotency-and-errors)).

13.8 **Compatibility.** A client SHOULD read `mak4i_whoami.protocol`
(§10.5). It SHOULD warn when the server's protocol MAJOR.MINOR differs
from the versions it supports, and continue only if the tools it needs
are listed.

13.9 **Check before create (guidance, non-normative).** Before creating a
record for a subject, a client should look for an existing current
record (`mak4i_get_current` or `mak4i_search`), and supersede it instead
of starting a competing lineage. This is a discipline that tooling
supports (for example an SDK `find_existing` helper). The protocol does
not enforce it, and the conflict model (MAK-0004) deliberately allows
competing lineages and surfaces them.

### §14 Change feed and MCP resources (optional profile)

14.1 **Purpose and scope.**
- A client that holds project knowledge can learn that the knowledge changed, and re-read it, without polling every tool.
- Two mechanisms, with different guarantees:
  - the **change feed** (§14.2–§14.4) is durable and ordered, and is the reliable way to catch up;
  - **MCP resource notifications** (§14.5–§14.7) are low-latency hints with no replay.
- Neither is the audit record ([MAK-0006 §8](MAK-0006.md#8-administration)), and neither carries record content.
- Implementations MAY offer this section. Those that do claim the `server-change-feed` profile ([CONFORMANCE](../CONFORMANCE.md#conformance-profiles)).
- *MCP resources* here are the MCP protocol's resources (`resources/list`, `resources/read`). They are unrelated to MAK-0009 resources (`resource_id`, resource groups), which have no binding at this revision (§10.7).

14.2 **Change events.**
- Every committed change to a project's governed knowledge produces exactly one change event in that project's feed, conforming to [`change-event.schema.json`](../schemas/change-event.schema.json).

| `kind` | Committed change |
|---|---|
| `record.created` | A new lineage was created ([MAK-0005 §A3](MAK-0005.md#a3-lineage-and-immutability)) |
| `record.superseded` | A new version superseded the head of a lineage ([MAK-0005 §A4](MAK-0005.md#a4-supersession-and-stale-head-protection)), including versions written by a resolution |
| `record.withdrawn` | A resolution withdrew a version ([MAK-0004 §A7](MAK-0004.md#a7-resolution)) |
| `resolution.completed` | A conflict resolution completed ([MAK-0004 §A7.6](MAK-0004.md#a7-resolution)) |
| `project.archived` | The project was archived |

- An event identifies:
  - **what changed:** `artifact_id`, `lineage_id`, `artifact_type`, `subject_key`, `previous_artifact_id`, `resolution_id` and `conflict_id` as applicable;
  - **who changed it:** `actor` with `principal_id`, `agent_id`, `auth_method` from the authenticated provenance ([MAK-0006 §7](MAK-0006.md#7-provenance)); `null` for a change made by instance-level recovery.
- When a record that is a candidate of an open or resolving conflict is created or superseded, its event carries that conflict's `conflict_id`.
- Events never carry record content, titles, rationale or reasons.
- Aborted or rejected operations produce no event: nothing was committed.

14.3 **Ordering and durability.**
- Each project feed has a `sequence`: a positive integer that strictly increases in commit order within the project. Gaps are allowed.
- A reader MUST NOT be given an event with sequence *n* while an event with a lower sequence in the same project can still commit. Implementations expose only events up to the **watermark**: the highest sequence below which every event has committed or has been abandoned.
- An event MUST be recorded for every committed change, including a change whose process stopped between committing the record and recording the event. Implementations MUST complete or reconcile such changes at start-up, as for pending resolutions ([MAK-0004 §A8.2](MAK-0004.md#a8-concurrency-idempotency-and-errors)).
- An event for an operation that did not commit MUST NOT become visible.
- Events are retained for at least 7 days (an implementation MAY keep them longer and SHOULD make the period configurable). The oldest retained sequence is the **floor**.

14.4 **`mak4i_changes` tool.**
- Requires `read` on `project` (scope `mak4i:read`).
- **Arguments:** `project`; `after`, an integer cursor, optional; `limit`, 1–500, default 100.
- **Result** (`structuredContent`): `{"events": [...], "next": <int>, "watermark": <int>, "more": <bool>}`.
  - `events` holds the committed events with `after` < `sequence` ≤ `watermark`, in ascending order, at most `limit`;
  - `next` is the cursor to pass as `after` next time;
  - `more` is true when further events up to the watermark exist.
- Without `after`, the result has **no events**, and `next` = `watermark`. A client starts following from "now".
- If `after` is below `floor − 1`, the call fails with `cursor_expired` and nothing else. The client re-reads current knowledge and continues from its `change_sequence` (§14.4a).
- `after` greater than the watermark is a `validation_error`.

14.4a **`change_sequence` in current knowledge.** A server claiming this profile MUST include `change_sequence` in every `mak4i_get_current` result: a project watermark taken **before** the result was computed. Every change with a sequence ≤ `change_sequence` is reflected in the result. A later change may already be reflected too, so clients MUST treat replayed events idempotently. "Read current, then `mak4i_changes(after=change_sequence)`" therefore never misses a change.

14.5 **MCP resources.** URIs use immutable identifiers only, never display names (organization and project IDs are globally unique):

| URI template | Content (`application/json`) |
|---|---|
| `mak4i://organizations/{organization_id}/projects/{project_id}/current` | The current knowledge result, as from `mak4i_get_current` without filters, including `change_sequence` |
| `mak4i://organizations/{organization_id}/projects/{project_id}/records/{artifact_id}` | One record version ([`project-record.schema.json`](../schemas/project-record.schema.json)); immutable except lifecycle pointers |
| `mak4i://organizations/{organization_id}/projects/{project_id}/conflicts/{conflict_id}` | One conflict ([`conflict.schema.json`](../schemas/conflict.schema.json)) |

- `resources/list` returns the `current` resource of every project the principal holds `read` on. The other forms are offered through `resources/templates/list`.
- `resources/read` requires `read` on the project (and scope `mak4i:read`), evaluated per request like a tool call.
- A URI for a project, record or conflict the principal can't read, or that doesn't exist, is refused with the same MCP error in both cases (MAK-0006 §5.5).
- Reading a resource is a read operation for audit purposes (MAK-0006 §8).

14.6 **Subscriptions and notifications.**
- Clients subscribe to resource URIs using the mechanism of the negotiated MCP revision:
  - `resources/subscribe` (2025-11-25);
  - the `resources` filter of `subscriptions/listen` (2026-07-28).
- A subscription to a URI the principal can't read MUST be refused, as in §14.5.
- After an event commits in a project, the server sends `notifications/resources/updated` for that project's `current` URI to every session subscribed to it. For `record.superseded`, `record.withdrawn` and `resolution.completed`, it also sends one for the affected record or conflict URIs those sessions subscribed to.
- The notification carries only the URI, never content. Clients re-read the resource, or call `mak4i_changes`.
- **Authorization at delivery.** Before delivering, the server MUST re-check that the session's principal is active, its credential or authorization is still valid, and it still holds `read` on the project. Otherwise the notification is not delivered. A principal that lost access learns nothing from the feed after that point.
- When the set of projects a session's principal can read changes (a grant created or revoked, a project archived), the server SHOULD send `notifications/resources/list_changed` to that session.

14.7 **Delivery semantics.**
- Notifications are best effort. They are not persisted, not replayed, and may be coalesced: one notification may stand for several events.
- A client that reconnects, or that needs certainty, MUST use `mak4i_changes` from its last cursor, or re-read current knowledge.
- Notifications are scoped to the connection that delivered them. A client MUST NOT act on a notification from one connection as if it came from another (§13.6).

14.8 **Security.**
- Events reveal identifiers, types, subject keys and the acting principal. That's metadata a reader of the project can already obtain from records and provenance, and nothing to a non-reader.
- Implementations SHOULD rate-limit `mak4i_changes` and subscriptions (§11.1).
- Feeds and subscriptions never cross organizations or projects.

## Examples

Unauthenticated request:

```
POST /team-a/mcp HTTP/1.1
Host: mak4i.example.com

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mak4i.example.com/.well-known/oauth-protected-resource/team-a/mcp", scope="mak4i:read mak4i:write"
```

Protected resource metadata:

```json
{
  "resource": "https://mak4i.example.com/team-a/mcp",
  "authorization_servers": ["https://mak4i.example.com/team-a"],
  "scopes_supported": ["mak4i:read", "mak4i:write", "mak4i:resolve"],
  "bearer_methods_supported": ["header"],
  "resource_name": "MAK4I"
}
```

## Security Considerations

- Token binding to the resource (§6.6) prevents a token issued for one
  MAK4I deployment being replayed at another.
- PKCE plus exact redirect matching protects public clients.
- Refresh rotation with replay revocation (§6.5) limits stolen refresh
  tokens.
- Prefix-separated token kinds (§2.2) prevent confusion and silent
  downgrade.
- SSRF controls on metadata fetches (§8.3).

## Interoperability Considerations

Hosted MCP clients typically reach servers from the public internet:
the resource identifier and issuer must be publicly reachable HTTPS
URLs. Clients that cannot reach `localhost` cannot use a local-only
deployment. Some clients choose Client ID Metadata Documents only when
the server advertises both `client_id_metadata_document_supported` and
`"none"` client authentication (§4.3).

## Backward / Forward Compatibility

New in this revision. Bearer principal credentials continue to work
unchanged (§2). Adding OAuth is additive for clients. Migrating to MCP
2026-07-28 auth in full (for example removing DCR) is a future revision.

## Conformance Requirements

A **server** implementation conforms to MAK-0008 when it satisfies §1–§12
for the transports and registration modes it enables, and additionally
§14 when it claims the optional `server-change-feed` profile. A **client**
(including an SDK) conforms when it satisfies §13 (the Client/SDK profile
in CONFORMANCE.md). Acceptance criteria:
[CONFORMANCE.md](../CONFORMANCE.md#mak-0008-mcp-binding-and-authorization).
