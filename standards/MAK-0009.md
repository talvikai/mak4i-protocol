## Abstract

This standard defines where MAK4I knowledge lives and how rules flow
between levels. It introduces:

- two knowledge profiles: **Project Records**, which stay within one
  project, and **Distributable Artifacts**, which an organization shares
  with its projects;
- **resources** (logical collections inside a project) and optional
  **resource groups**;
- **rules** with an explicit `enforcement` of `default` or `mandatory`,
  inherited from the organization down to resources, with explicit and
  attributable overrides.

It is an **architecture** standard at this revision. It fixes the model
so that later implementations and interface bindings agree. It does not
yet define tools, error codes or conformance criteria (§8).

## Motivation

Teams keep requirements, issues, decisions and rules in a project, and
some rules belong to the whole organization ("all services log in
JSON"). Without a shared model:

- implementations would disagree on whether organization knowledge
  reaches a project;
- they would disagree on whether a project may change an organization
  rule;
- they would disagree on how to tell an override from an unrelated rule
  with similar wording.

Readers also need to know *which* rule applies and *where it came from*.

## Scope

- Knowledge profiles and their scopes.
- The organization → project → resource group → resource hierarchy.
- Resource and resource-group identity.
- Rule identity, the enforcement field, inheritance, override targeting
  and effective-rule computation.
- How these interact with conflicts (MAK-0004), versioning (MAK-0005) and
  authorization (MAK-0006).

## Non-Goals

- Public or cross-organization distribution. A public registry is
  [MAK-0007](../STANDARDS.md) (planned) and is **not** implied here.
- Context assembly and injection ([MAK-0002](../STANDARDS.md), planned).
  This standard defines the effective rules that such assembly would
  consume.
- Resource-group or resource-level **grants**. They are future; §7
  defines only how they will relate to project grants.
- Explicit deny permissions.
- Provisioning infrastructure. A resource is a knowledge collection, not
  a cloud asset (§3.6).
- Guaranteeing that an AI system obeys a rule (§4.9).

## Terminology

| Term | Definition |
|------|-----------|
| **Scope** | One node of the hierarchy: an organization, a project, a resource group or a resource (§1). |
| **Project Record** | Knowledge kept within one project ([MAK-0005 Part A](MAK-0005.md#part-a--governed-project-records-normative)). Not shared with other projects (§2.1). |
| **Distributable Artifact** | Knowledge owned by an organization and shared with that organization's projects (§2.2). |
| **Revision** | A project record's position in its lineage, carried in the record field `version` (`"1.0"`, `"2.0"`, …) (§2.3). |
| **Package version** | The semantic version of a Distributable Artifact (§2.3). Not a revision. |
| **Resource** | A logical collection inside one project, for example *Requirements*, *Issues* or *Rules* (§3). |
| **Resource group** | An optional grouping of resources inside one project (§3.2). |
| **Rule** | A project record or distributable artifact that carries a `rule` object (§4.1). |
| **Enforcement** | The rule field `enforcement`: `default` or `mandatory` (§4.3). |
| **Override** | A rule at a lower scope that explicitly declares that it replaces the inherited rule with the same `rule_key` (§4.4). |
| **Effective rule** | The rule that applies at a scope after inheritance, overrides and enforcement are evaluated, together with its explanation (§4.6). |

## Normative Requirements

### §1 Scope hierarchy

1.1 Knowledge is organized in two logical hierarchies:

```
Organization ─▶ Project ─▶ Resource
Organization ─▶ Project ─▶ Resource Group ─▶ Resource
```

1.2 A scope is referenced as `{"type": "organization" | "project" |
"resource_group" | "resource", "id": "<identifier>"}`
([`common.schema.json#/$defs/scopeRef`](../schemas/common.schema.json)).

1.3 The **scope chain** of a scope is the path from its organization
down to it:

| Scope | Chain |
|---|---|
| organization O | O |
| project P | O → P |
| resource group G | O → P → G |
| resource R | O → P → R, or O → P → G → R when R is a member of G |

1.4 Every chain lies within **one organization**. Nothing in this
standard lets knowledge, rules or inheritance cross an organization
boundary ([MAK-0006 §1](MAK-0006.md#1-organizations)).

### §2 Knowledge profiles

2.1 **Project Record.**
- A project record is a governed record as defined by
  [MAK-0005 Part A](MAK-0005.md#part-a--governed-project-records-normative).
  It belongs to exactly one project.
- It is **not** visible as knowledge of any other project. Neither
  inheritance nor resource grouping changes this.
- It keeps its own identity (`artifact_id`, `lineage_id`), its revisions
  and its authenticated provenance
  ([MAK-0006 §7](MAK-0006.md#7-provenance)).
- It MAY be attached to one resource of the same project (§3.4).

2.2 **Distributable Artifact.**
- A distributable artifact belongs to exactly one organization and is
  shared with **that organization's** projects
  ([`distributable-artifact.schema.json`](../schemas/distributable-artifact.schema.json)).
- **Inheritance and applicability.** A distributable artifact applies to
  **every project of its organization** unless it lists `targets` (a
  non-empty list of project ids of that organization), in which case it
  applies only to those projects. Projects can't opt out of an applicable
  artifact. Targeting by resource group is reserved for a later revision.
- **Source retention.** When a project consumes an organization
  artifact, the consumed item MUST retain its source identity
  (`organization_id`, `artifact_id`), its `package_version` and its
  provenance. A consuming project MUST NOT re-attribute it, re-version it
  or silently copy it into a project record.
- **No cross-organization reach.** Organization scope never grants access
  to another organization.
- **Lifecycle.** Each artifact has a `status`:
  - `active`: applies.
  - `deprecated`: still applies, and SHOULD name its replacement in
    `deprecated_by` (the same artifact id convention as MAK-0001's
    `deprecated_by`).
  - `withdrawn`: no longer applies to any project; its history is kept.
  
  Status changes don't alter any published package version.
- **Version consumption.**
  - By default a project consumes the **latest published package
    version** of each applicable artifact.
  - A project MAY pin an artifact to one published `package_version`
    ([`artifact-pin.schema.json`](../schemas/artifact-pin.schema.json)).
  - An artifact that carries a `mandatory` rule always applies at its
    latest published version, whatever the pin.
  - A pin to a withdrawn artifact has no effect.
- **Packaging metadata.** A distributable artifact's descriptive fields
  MAY follow [MAK-0001](MAK-0001.md):
  - MAK-0001 `id` ↔ `artifact_id`;
  - `version` ↔ `package_version`;
  - `name` ↔ `title`;
  - `description` / `content` ↔ `content`;
  - `deprecated` / `deprecated_by` ↔ `status: deprecated` / `deprecated_by`;
  - `type` (procedural / semantic / episodic) MAY be carried as
    `artifact_type`.

2.3 **Revisions vs package versions.**
- A project record revision is the lineage position defined by
  [MAK-0005 §A2](MAK-0005.md#a2-record-fields), carried in the field
  `version` (pattern `"<n>.0"`). The field name is kept for
  compatibility.
- A distributable artifact's `package_version` is a semantic version
  (`MAJOR.MINOR.PATCH`). What MAJOR/MINOR/PATCH mean for knowledge is
  approved future scope (F-9; [MAK-0005 D-001](MAK-0005.md#decision-d-001--version-representation-and-semantics)).
- Implementations MUST NOT compare, order or convert a revision and a
  package version against each other.
- Each published `package_version` of a distributable artifact is
  immutable.

### §3 Resources and resource groups

3.1 **Resource**
([`resource.schema.json`](../schemas/resource.schema.json)):
- A resource has a stable `resource_id`, a `name` and a `resource_type`.
- `resource_id` is unique within its organization and MUST NOT be
  reused.
- **Lifecycle.** A resource is `active` or `archived`. Resources are
  archived, never deleted
  ([MAK-0006 §8.4](MAK-0006.md#8-administration)). An archived resource
  keeps its records and their history, and accepts no new records.
- **Names.** A resource's `name` is unique among the active resources of
  its project (compared exactly after trimming).
- `resource_type` is an **open, extensible** vocabulary (for example
  `requirements`, `issues`, `rules`). Implementations MUST NOT hard-code
  collection types into core behavior. Two resources of different types
  pass through identical code.
- Every resource belongs to **exactly one project**.

3.2 **Resource group**
([`resource-group.schema.json`](../schemas/resource-group.schema.json)):
- A resource group has a stable `group_id` and a `name`, and belongs to
  exactly one project.
- Groups provide a management scope, a rule-inheritance scope (§4) and a
  future permission scope (§7).
- Groups MUST NOT be nested.
- **Lifecycle and names.** Groups have the same lifecycle and name rules
  as resources. Archiving a group requires that it has no active member
  resources.

3.3 **Membership.**
- Membership is optional.
- A resource is a member of **at most one** group, which MUST be in the
  same project. It is recorded as the resource's `group_id`, or `null`
  for no group.

3.4 **Records and resources.**
- A project record MAY carry `resource_id`, which attaches it to one
  resource of **the same project**. A record without `resource_id` is
  project-wide.
- The resource is the collection; the record holds content and revision
  history. For example, a *Requirements* resource contains individual
  requirement records.
- **Moving a record.** A record MAY move to another active resource of
  the same project, or become project-wide. A move:
  - is an authorized, audited metadata change (§3.7), not a new revision;
  - changes only `resource_id`;
  - keeps the record's identity, lineage, revisions, content and
    provenance.

3.5 **Moving a resource between groups.**
- A move changes only the resource's `group_id`. Its `resource_id`, its
  attached records and their history are preserved.
- Because membership changes the inherited rules (§4) and, later,
  permissions (§7), an implementation MUST authorize membership changes
  and record them as attributable administrative events
  ([MAK-0006 §8.5](MAK-0006.md#8-administration)). Membership changes
  require the `govern` permission (§6).

3.6 **Not infrastructure.** Creating, renaming or archiving a resource
MUST NOT provision, change or delete any external system or cloud asset.

3.7 **Audit events.** When implemented, these actions are administrative
events ([MAK-0006 §8.5](MAK-0006.md#8-administration)), successful or
denied:

| Action | Event `action` |
|---|---|
| Create, rename or archive a resource | `resource.create`, `resource.rename`, `resource.archive` |
| Create, rename or archive a group | `resource_group.create`, `resource_group.rename`, `resource_group.archive` |
| Move a resource into, out of or between groups | `resource.move` |
| Move a record to another resource, or make it project-wide | `record.move` |
| Change a rule's `enforcement` | `rule.enforcement_change` (with the resulting effective-rule transitions, §4.6) |
| Publish, deprecate or withdraw a distributable artifact | `artifact.publish`, `artifact.deprecate`, `artifact.withdraw` |
| Pin or unpin an artifact for a project | `artifact.pin`, `artifact.unpin` |

### §4 Rules, enforcement and inheritance

4.1 **Rule.** A rule is a project record or a distributable artifact
that carries a `rule` object
([`rule.schema.json`](../schemas/rule.schema.json)) with:

| Field | Meaning |
|---|---|
| `rule_key` | Stable rule identity within the organization (§4.2). |
| `enforcement` | `default` or `mandatory` (§4.3). REQUIRED on every rule. |
| `applies_to` | The scope where the rule applies (§4.2). |
| `overrides` | `null`, or `{"scope": <scopeRef>}` naming the ancestor scope whose inherited rule this one replaces (§4.4). |

The rule's text is the record's or artifact's `content`. Interpreting
that text is outside this standard (§4.9).

4.2 **Rule identity and placement.**
- **Key.** `rule_key` is normalized like a subject key: Unicode NFC,
  trimmed, non-empty, at most 512 characters, compared exactly
  ([MAK-0005 §A5.2](MAK-0005.md#a5-subject-keys)).
- **Identity.** A rule's identity is the pair (`applies_to` scope,
  `rule_key`). Successive revisions or package versions of the same rule
  keep that identity.
- **Where `applies_to` may point.** It names the scope where the rule
  applies:
  - for a distributable artifact, its organization;
  - for a project record, its project, or a resource group or resource of
    that project.
- **Placement is independent of storage.** A rule's reach is its
  `applies_to` field only. Which resource stores the rule record (§3.4) is
  organizational. Moving the record to another resource never changes
  what the rule governs.
- **No inference.** Implementations MUST NOT treat two rules as related
  because of similar wording, titles or tags. Only `rule_key` and
  `overrides` establish relationships.

4.3 **Enforcement.**
- `enforcement` is a dedicated field. Tags, titles or content MUST NOT set
  or change enforcement.
- A `default` rule is inherited by every scope below `applies_to` and MAY
  be explicitly overridden at a lower scope.
- A `mandatory` rule is inherited by every scope below `applies_to` and
  MUST NOT be overridden or downgraded at a lower scope.
- A lower scope MAY override an inherited `default` rule and mark its own
  rule `mandatory`. That rule then binds every scope below it.
- Overrides can only be permitted again by an authorized principal
  changing the rule **at the scope where mandatory enforcement was
  established**: a new revision or package version with `enforcement:
  "default"`, by a principal authorized at that scope (§6).

4.4 **Overrides.**
- An override is a rule at scope S, with the same `rule_key` as an
  inherited rule, whose `overrides.scope` names an ancestor of S in S's
  scope chain that holds a rule with that key.
- An override MUST NOT modify the parent rule, and it has no effect on
  sibling scopes or on any scope outside S's subtree.
- The override relationship is stored explicitly and preserved across
  revisions.

4.5 **Write-time checks** (when implemented):
- **(a) Mandatory ancestor.** A write that would create or revise a rule
  at scope S with key K MUST be rejected without effect if an ancestor of
  S holds an active `mandatory` rule with key K.
- **(b) Undeclared override.** It SHOULD be rejected if an ancestor holds
  a rule with key K and the new rule does not declare `overrides`.
- **(c) Invalid target.** It MUST be rejected if `overrides.scope` is not
  an ancestor holding a rule with key K.
- Error codes are defined together with the interface binding (§8.4).

4.6 **Effective rule computation.**
- **Inputs.** Given a target scope T and key K, consider the active rules
  with key K whose `applies_to` lies on T's scope chain, top-down.
- **Valid rules.** A rule at the top-most scope of the chain is valid. A
  rule at a lower scope is valid only if:
  - it declares `overrides` naming an ancestor that holds a rule with
    key K; and
  - no valid `mandatory` rule with key K exists strictly above it.
- **Effective rule.** It is the top-most valid rule whose enforcement is
  `mandatory`, if there is one. Otherwise it is the lowest valid rule.
- **Same-scope conflicts.** Two or more current rule lineages with key K at
  the same scope are a conflict (§4.7).
  - **Mandatory ancestor.** If a valid `mandatory` rule above that scope
    exists, it decides K. The conflicting candidates stay preserved and
    inspectable, reported as `blocked_by_mandatory`.
  - **Otherwise conflicted.** K is reported as **conflicted** at that
    scope and at every descendant scope, and no candidate is chosen.
  - **No bypass.** There is no fallback to an ancestor `default`, and no
    descendant override may bypass the conflict, because the candidates
    may disagree about enforcement as well as content.
- **Required explanation.** The result
  ([`effective-rule.schema.json`](../schemas/effective-rule.schema.json))
  MUST identify:
  - the effective rule, with its source identity, revision or package
    version, enforcement and originating scope;
  - every rule on the chain with its status: `effective`, `overridden`,
    `blocked_by_mandatory`, `override_not_declared` or `conflicted`;
  - the provenance of each listed rule.
- **Blocked overrides (preserve and reactivate).**
  - A lower rule blocked because an ancestor is (or became) `mandatory` is
    never retired or rewritten. It is reported as `blocked_by_mandatory`.
  - When the establishing rule returns to `default`, the blocked rule
    becomes eligible again automatically. It is subject to the current
    validity and conflict checks of this section.
  - A blocked rule does not reactivate if its own lineage was withdrawn or
    superseded in the meantime. Only the current head of a lineage takes
    part.

4.6a **Changing mandatory back to default.** An implementation MUST:
- before applying the change, show the requester the overrides that
  would become effective again;
- record the change and the resulting effective-rule transitions as an
  attributable `rule.enforcement_change` event (§3.7);
- explain, in the effective-rule result, which override now applies and
  why.

4.7 **Conflicts.**
- Competing contributions to one rule at the **same scope** are subject
  to conflict handling, with the same principles as
  [MAK-0004 Part A](MAK-0004.md#part-a--subject-conflicts-normative):
  - deterministic detection;
  - no newest-wins;
  - explicit resolution;
  - preserved history.
- The subject of a rule conflict is (organization, `applies_to` scope,
  `rule_key`). Scope identity is the organization, project, resource-group
  or resource id.
- **Same lineage vs different lineages.** A new revision of the same
  lineage supersedes the previous one. Separate competing lineages
  conflict.
- **Resolution.** Conflicts are resolved explicitly, with MAK-0004 Part A's
  actions (`select_winner`, `merge`, `separate_subjects`, where
  separation assigns a different `rule_key`) and its record, idempotency
  and audit requirements, applied at the rule's scope.
- **Effect on effective rules** is defined in §4.6.
- **Status.** This generalization is decided protocol behavior. Its
  implementation at each scope is scheduled separately (§8).
- Contributions at **different** scopes are not conflicts; inheritance
  and overrides (§4.4–§4.6) govern them.

4.8 **Access.**
- Rule precedence MUST NOT bypass access grants. Computing an effective
  rule MUST NOT disclose a rule the requester is not permitted to read.
- **Inherited organization artifacts.** `read` on a project covers the
  distributable artifacts that apply to that project (§2.2), and only
  those. No separate organization read grant exists.

4.9 **No compliance guarantee.**
- MAK4I governs which rules form the **effective context** and explains
  why.
- It does not and cannot guarantee that an external AI system follows an
  instruction it receives. Implementations and documentation MUST NOT
  claim otherwise.

### §5 Versions and attribution of rules

5.1 Rules are revised like the knowledge that carries them:
- project-record rules by supersession, with stale-head protection
  ([MAK-0005 §A4](MAK-0005.md#a4-supersession-and-stale-head-protection));
- distributable-artifact rules by publishing a new immutable
  `package_version`.

5.2 Every revision or package version carries authenticated provenance
([MAK-0006 §7](MAK-0006.md#7-provenance)), including changes of
`enforcement` and of `overrides`.

### §6 Organization knowledge

6.1 Organization-level knowledge (distributable artifacts and
organization rules) is part of the protocol architecture.

6.2 **Who may change what** (architecture-defined; enforced when
implemented):

| Action | Required |
|---|---|
| Publish, deprecate, withdraw or target a distributable artifact; write, revise or change the enforcement of an organization rule | Organization owner ([MAK-0006 §8.2](MAK-0006.md#8-administration)) |
| Set or remove `mandatory` on a project, group or resource rule | `govern` on the project |
| Create, rename or archive resources and groups; change group membership; move records between resources | `govern` on the project |
| Write or revise a `default` rule at project, group or resource scope (no change of enforcement) | `write` on the project |
| Pin or unpin an artifact for a project | `govern` on the project |

`govern` is a project permission defined in
[MAK-0006 §5.1](MAK-0006.md#5-permissions-and-grants). Like `resolve`,
it implies neither `read` nor `write`, and it confers no administrative
rights over the organization.

### §7 Authorization: current and future

7.1 **Current model.** Project grants
([MAK-0006 §5](MAK-0006.md#5-permissions-and-grants)) are the only
authorization unit. A project permission governs every resource and
resource group in that project.

7.2 **Future grants.**
- Resource-group and resource-level grants are future work.
- When they are defined, they will be **additive**: a narrower grant can
  add permissions on part of a project, and it never revokes or narrows
  a broader project grant.
- This standard introduces no explicit deny.

7.3 **No implied restriction.** Until such grants exist, metadata that
describes a resource or group MUST NOT be presented as an enforced access
restriction. This includes its type, its group, its name, and any field
or tag that looks like an access label.

### §8 Conformance status at this revision

8.1 This standard is **architecture-defined**:
- it has no acceptance criteria in [CONFORMANCE.md](../CONFORMANCE.md);
- its schemas are marked `"x-mak4i-status": "architecture"`;
- no [MAK-0008](MAK-0008.md) tool exposes it.

8.2 An implementation MUST NOT claim support for MAK-0009 at this
revision, and the architecture-defined fields of other schemas
(`resource_id`, `rule` in project records) are not required by any
conformance profile.

8.3 The current Reference implementation (protocol revision `62fca93`)
implements none of §2.2, §3, §4, §6 or §7.2. Its project records remain
conformant without these fields.

8.4 **Binding deferred (approved future scope).** The
[MAK-0008](MAK-0008.md) tool binding, the error codes and the conformance
criteria for this standard are written in the milestone that implements
it, protocol first. Until then this standard stays architecture-defined.

## Examples

Organization default rule, project override marked mandatory, and a
resource in a group:

```json
{"artifact_id": "logging-standard", "organization_id": "org_42", "package_version": "1.2.0",
 "artifact_type": "engineering_rule", "title": "Structured logs", "content": "Services log JSON.",
 "rule": {"rule_key": "logging.format", "enforcement": "default",
          "applies_to": {"type": "organization", "id": "org_42"}, "overrides": null}}
```

```json
{"artifact_id": "payments-logging", "project": "prj_pay", "version": "1.0",
 "rule": {"rule_key": "logging.format", "enforcement": "mandatory",
          "applies_to": {"type": "project", "id": "prj_pay"},
          "overrides": {"scope": {"type": "organization", "id": "org_42"}}}}
```

Effective rule for `logging.format` at any resource of `prj_pay`: the
project rule. Its originating scope is `prj_pay`, it is `mandatory`, and
the organization rule is reported as `overridden`. A resource-level rule
with the same key there would be `blocked_by_mandatory`. Other projects
of `org_42` still get the organization default.

## Security Considerations

- Organization scope never crosses organizations (§1.4).
- Inheritance does not widen authorization (§4.8, §7).
- Overrides are explicit, so an attacker cannot "override" a rule by
  writing similar text (§4.2).
- Resource metadata is not an access control (§7.3).
- Effective context is advisory to external AI systems (§4.9).

## Backward / Forward Compatibility

- **Additive.** Existing project records (no `resource_id`, no `rule`)
  remain valid and are project-wide, non-rule knowledge. No migration is
  implied.
- **Reserved names.** The new record fields are reserved and optional.
  Implementations that don't support MAK-0009 MUST NOT emit them.
- **Future bindings.** Tool bindings and error codes will be added in a
  later revision of [MAK-0008](MAK-0008.md).
